# Test bridge

Tooling that lets an agent drive and read the game on the Windows PC without Peter's hands. Built 12 October 2026 after the 0.9.8 agent run, where Peter had to walk, drive and click world objects for the agent, notices faded before the agent could read them, and the clock kept running while the agent worked.

The pieces:

| Piece | Where | What it does |
|---|---|---|
| Notice log | `unity/FoodTrucks/Scripts/` | Every notice and phone text the mod shows is also a `Notice:` or `Phone:` line in `Player.log` |
| Test bridge | `unity/FoodTrucks/Scripts/TestBridge*.cs` | HTTP on `127.0.0.1:8330` inside the game, only when the game was launched with `-foodtrucks-test` |
| `tools/ft` | Mac | Command-line client for the bridge |
| `tools/ft-mcp` | Mac | The same calls as an MCP server (stdio), registered in `.mcp.json` |
| `tools/mock-bridge` | Mac | A fake bridge with canned state, for working on the client and scenarios without the game |
| `tools/scenario` | Mac | Runs a scenario file (steps and checks) against the bridge, writes a report |
| `tools/check-log` | Mac | Checks a `Player.log` against a build's expected log lines |
| `tools/contact-sheet` | Mac | One HTML page of the screenshots a run took |
| `tools/run-remote.sh` | Mac → homepc | Starts the game in Peter's desktop session with the test flags, opens the ssh tunnel, stops the game |
| Soak test | `tests/` | Many simulated days through Core with seeded random play, checking invariants |

## Safety

- The bridge starts only with `-foodtrucks-test` on the game's command line. Without it nothing listens, and the Workshop build behaves as before.
- It binds `127.0.0.1` only. The Mac reaches it through `ssh -L 8330:127.0.0.1:8330 homepc` (`tools/run-remote.sh tunnel`).
- Commands that change a save (money, spawns, time jumps, debug actions) are for throwaway **FT** saves only. `load` and `new_game` refuse any save whose name doesn't start with `FT`, and the bridge refuses every changing command while the loaded save's name doesn't start with `FT`.


### Sharing the game PC

Several sessions test on homepc. `C:\Users\Peter\game-lock.txt` says who has the game: no file means free; the holder writes `owner:`, `since:`, `until:`, `game:` (what runs) and `rules:` lines and deletes the file when done. While another session holds it: no install, start, stop, quit or save load, and no bridge calls that change the game (`health`, `state` and `/events` are fine). `tools/run-remote.sh lock [minutes] [what]` and `unlock` take and release it under `BA_LOCK_OWNER` (default `Food Trucks session`); `start`, `stop` and `tools/install-remote.sh` refuse while someone else holds it, and `status` shows it.

## Local macOS testing

The manifest targets Windows and Mac. `tools/build-mod.sh` packages and checks both bundles; Unity needs both platform modules. With Big Ambitions closed, run `python3 tools/install-local-mac.py`. It verifies every staged file against `build/FoodTrucks.sha256`, replaces only `ModsLocal/FoodTrucks`, and preserves the previous package under `FoodTrucksPackageBackups` outside ModsLocal. Other installed mods and saves stay in place. The default game data folder is `~/Library/Application Support/com.Hovgaard-Games.Big-Ambitions`; `--game-root` overrides it for another local installation.

Launch the installed Steam game with `-foodtrucks-test`, for example from the shell (Steam must be running):

```sh
open "$HOME/Library/Application Support/Steam/steamapps/common/Big Ambitions/Big Ambitions.app" --args -foodtrucks-test

```

Use a separate FT character as required by the bridge's save guards. The existing clients connect directly to `http://127.0.0.1:8330`; no PC or SSH tunnel is needed. `BA_BRIDGE_URL` can override that address. Screenshots reported as local paths are copied directly by the tools. Quit through the game's menu before installing another build; `tools/ft call quit` is also available while the bridge is active, subject to its save guards. The installer never starts or stops the game.

## Transport

All bodies are UTF-8 JSON. Every reply has `ok` and, next to it, `session`: 8 hex characters the bridge picks at random each time it starts. A different `session` means the game or the mod restarted, and nothing a client knew from before (operation numbers, event numbers, state) holds. A `/call` body may carry `"expect_session": "<8 hex>"`; when it differs from the current session the call is refused before it is numbered or queued: `{ "ok": false, "session": "<current>", "error": "the bridge restarted (session <current>); reconnect first." }`. A failed call has `ok: false` and `error` (one sentence a person can act on).

### `GET /health`

Answered on the HTTP thread from values the main thread refreshes every frame, so it works while the game loads.

```json
{ "ok": true, "session": "3f9a1c07", "mod_version": "0.9.10", "bridge_version": 1, "scene": "menu|loading|city", "save": "FT bridge", "day": 3, "time": "14:05", "paused": false, "time_skip": false, "frame": 123456, "load": { "name": "FT bridge", "status": "pending|done|failed" } }
```

### `POST /call`

```json
{ "cmd": "state", "args": { } }
```

Runs on the Unity main thread, one call after another. The HTTP thread waits up to `timeout_s` (default 10, an `args` field) for the result; past that the reply is `ok: false, error: "timed out on the main thread; …"` and the command still finishes in the game. Reply: `{ "ok": true, "op": 17, "result": { … } }`, or `{ "ok": false, "op": 17, "error": "…" }`.

Every call gets an operation number `op`. `{ "cmd": "op", "args": { "id": 17 } }` answers at once, whatever the main thread is doing, with `{ "ok": true, "result": { "id": 17, "cmd": "save", "session": "3f9a1c07", "status": "pending|done|failed", "result": { … }, "error": "…" } }` (`result` only when done, `error` only when failed). After a timeout, ask this instead of sending the call again. The bridge keeps every pending operation and the last 500 completed operations, ordered by completion.

Each request is served on its own thread, so `/health`, `/events` and `op` answer while a `/call` waits.

### `GET /events?since=N`

The bridge keeps the last 2,000 events in a ring buffer: every line the mod logs (`Log.Info`, `Log.Error`), every notice and phone text, and Unity errors and exceptions from any source. Reply:

```json
{ "ok": true, "next": 812, "dropped": 0, "events": [ { "seq": 811, "real": "2026-10-12T14:03:11.204Z", "day": 3, "time": "14:05", "kind": "log|error|notice|phone|unity_error", "text": "…" } ] }
```

`next` is the `since` to pass next time. `dropped` counts events that fell out of the buffer between `since` and the oldest kept.

An event's `day` and `time` are the game clock when the line was written: read directly when the line comes from the main thread in the city, else the clock of the frame's `/health` snapshot. `/health` and the stamps read the same clock, so a stamp that differs from a later `/health` means the clock moved in between. The bridge logs any jump of more than 30 game minutes in one frame, once the jump has settled: `Test bridge: the clock jumped from day 1 08:44 to day 1 11:47 in one go: <why>.`, where `<why>` is `a time skip (sleep or a paid activity)`, `the player collapsed (hospital)` or `something set the time (the game, a load or another mod)`. Live session 4 saw `load 'FT bridge' done` stamped 08:44 and `/health` say 11:47 seconds later; the stamps and `/health` already shared one clock then, so the clock itself jumped (cause not seen; the jump line names it next time). `time_skip` in `/health` is true while the game's time skip runs.

## Game side, as built

Built 12 October 2026 in `unity/FoodTrucks/Scripts/` (`Notices.cs`, `TestBridge*.cs`). Not yet run in game; every game call below comes from the 1.0 decompile, and the ones to check first are listed in CHECKS.md, "Test bridge". Where the build differs from the contract above, this section wins.

**Startup.** One line at the mod's initialisation load: `Test bridge: listening on http://127.0.0.1:8330/ (session 3f9a1c07).` or `Test bridge: off (the game was started without -foodtrucks-test).` A taken port logs `Test bridge: could not listen on 127.0.0.1:8330 (…); … The bridge is off.` With the flag the bridge also sets `Application.runInBackground`, so the game keeps running when its window loses the focus. `Test bridge: stopped.` when the mod unloads.

**Collision log.** With the flag, a postfix on NWH's `VehicleController.OnCollisionEnter` logs each collision of a food truck (the cart has no NWH controller) that passes NWH's crash-sound filter (contact points, and any layer but Ground, GroundUnplacable and Roads, as `DamageHandler.IsCollisionValid`), at most one line per 0.25 s for each vehicle and object hit: `Collision (test bridge): truck <id> hit <collider> on <root> (layer <layer>) at x …, y …, z … on the vehicle (x right, z forward), our <collider>; relative speed … m/s, vehicle … km/h; passes NWH's crash-sound filter.` Added 13 October 2026 for the crash sound Peter hears when steering hard (CHECKS D6).

**Notice log.** Every notice the mod shows is a `Notice: <text>` line and every text it sends a `Phone: <contact>: <text>` line, with the text resolved as the game shows it (`LocalizorManager.Localize(key, data)`). A key the game has no text for is logged as `<key> {name=value, …}`. The player's own line in a call (the commissary order read-back) is `Phone: <contact>: [player] <text>`. What the player sees is unchanged.

**FT guard.** `console`, `debug`, `time`, `money`, `teleport`, `vehicle`, `commissary`, `crew`, `fixture`, `logistics run`, `save`, `ui click` and `ui escape` need the city and a loaded save whose name starts with `FT`. For `ui click` and `ui escape` the refusal reads `ui works only in a loaded FT city; use load from the main menu.` They also refuse when the save's character folder holds a save whose name doesn't start with FT (the game's own `Recover #N` and `Recover Midnight` aside): `This save's character also has saves not starting with FT (<first name>); make FT saves with a character of their own.` `load` checks the same for the save it loads (and, from the city, for the city it leaves). So make FT saves from a new character of their own, never by saving a series city under a new name. `state`, `ui list`, `shoot`, `logistics status`, `op` and `quit` work with any save. `load` from the city needs an FT city. `save`, `load` and `new_game` take only names that start with `FT`.

**Scene.** `menu` covers the main menu and the character creator; `loading` covers the loading screen and the step between a save and the city; `city` is the city with a save loaded.

**`/events`.** `since` is the first number wanted: the reply has the events numbered `since` and later, and `next` is the number after the newest. Numbers start at 1. The mod's own error lines arrive once, as `error`, not again as `unity_error`.

**Unload.** Each HTTP server is started under one bridge generation and stamps every request it accepts with it, so a request the old server takes during a stop never counts as the new generation. Taking a call into the main thread's queue and stopping share one lock: a call whose generation has ended by then (a stop, perhaps a start, came in between) is refused with `the bridge stopped`, and the main thread also fails any queued call from an earlier generation instead of running it. When the mod unloads, the bridge stops taking calls, fails every queued and pending call with `the bridge stopped` (a shot's camera and texture are released), and clears its operations, events, run_until and load status, so a start after the mod is enabled again begins clean.

**Error lines.** Every line the mod logs through `Log.Error` starts `ERROR: ` (once), after the game's `[Mod:Food Trucks]` prefix; the `error` events carry the same text.

**Operations.** `timeout_s` is clamped to 1…600 before the call is queued. Every `/call` reply carries `op`, and `{ "cmd": "op", "args": { "id": N } }` gives that call's status (see `POST /call`). Requests are served each on their own thread; the calls still run one after another on the main thread.

**`/call` that finish later.** `save` (until the file is written), `teleport` of the player (until the move out of a building or vehicle ends) and `shoot` (8 frames) answer when they finish, within `timeout_s`. Past it the reply is `timed out on the main thread` and the work still finishes.

**`time`.** `speed` multiplies the player's own game speed from Options (`GameManager.SetMinutesMultiplier`), from above 0 to 60; 1 is normal play. `speed` alone also unpauses. `run_until` takes `day` as a number or `"+N"` (days from today; default today) and `time` as `"HH:MM"`; it runs the clock at `speed` (default 1), checks every frame, and at the time pauses (the game's own pause, `SetPlayerPause`) and sets the speed back to 1. With the bridge on, a Harmony prefix on `GameManager.RunMainGameTick` (logged `Patch GameManager.RunMainGameTick(Single), test bridge run_until: Active.`) keeps any step of the clock from going more than 0.01 of a minute past the target, and the run counts as arrived only once the minute the game shows is the target, so it stops on that minute (its hour's events included, for a target on the hour). Live session 5 stopped once at 16:04 for 16:05: the old check took 16:04.999 as arrived. `state.clock.run_until` is the target while it runs; `state.clock.arrived_at` is where it stopped ("day D HH:MM") until the next `time` call. `keep_needs` (added 13 October 2026 after live session 4, where two game days of `run_until` ended in a collapse, a clock jump to 08:00 the next day and a $2,000 hospital bill): on by default for `run_until`, off for `speed` alone, and given as `true` or `false` on either; a pause turns it off, and so do reaching the `run_until` target and leaving the city. **`teleport`.** For an `x`, `z` move the bridge reads every surface of the game's Ground layer stacked at that point (a street under an elevated road) and takes, with an explicit `y`, the surface nearest it within 1.5 m (for the player, a walkable one); otherwise a walkable one nearest the mover's own height; otherwise the one nearest that height (Core `GroundPick`). Walkable, for the player, means NavMesh of the player's own agent type and areas within the 3 m the landing allows and within 1 m of the surface's height and, while the player stands on the NavMesh within 100 m of the target, a complete walking route from there (longer routes come back partial in the city, so beyond 100 m they aren't checked). The deck at x -1490, z -1150 that live sessions 4 and 6 took for a highway is the game's walkable bridge (`BridgeMiddleRoad`, with NavMesh, a walking route from the street, and people and benches on it), so a `y` of 5.06 there lands on it; a refusal needs ground with no walkable NavMesh, such as x 412, z 200 inside a Hell's Kitchen block. `surface` ends `; walking routes checked from the player's place`, `; walking routes not checked (more than 100 m from the player)` or `; walking routes not checked (the player isn't on the NavMesh)`. A vehicle's surfaces are read with any NavMesh. A player move with no walkable surface at all is refused too, even when it is the only surface there (`No walkable ground at x …, z …: no walkable surface of 1: 5.06 not walkable; …`); a vehicle keeps the fallback. An explicit `y` with no such surface is refused: `No walkable ground at x …, z … near y 5.06: no walkable surface within 1.5 m of the y asked for (5.06); surfaces there: 0.20 walkable.` (`No ground …` for a vehicle). The player's landing must also be within 1 m of the chosen surface's height, so a NavMesh on another level never takes them there. Live session 5: a reply said "nearest the mover's height (0.09) of 2: 3.22, 0.20" and took 3.22 because the street read as not walkable with a 1 m search, and a `y` of 5.06 over a street put the player on the street; the reply now lists each height as walkable or not. The player's navigation is reset first (`PlayerController.ResetNavigation`, which also drops a Back to the hatch walk), then the player goes through the game's `GameManager.SetPlayerPosition` (out of a building or garage first, then a NavMesh warp) after leaving the hatch or the driver's seat, and must land within 3 m of walkable ground. Before either moves, the bridge tests the place for anything else standing there, from 0.3 m above the ground up: for a vehicle its own footprint, for the player a standing person's capsule. The footprint is the box round its solid colliders' own shapes (a box collider's size, a sphere's or capsule's enclosing box, a mesh's local bounds) carried into the vehicle's frame with their scale (Core `Footprint`), so it is the same whichever way the vehicle faces; the bridge logs it once per vehicle type: `Test bridge: footprint of <type>: … m across, … m long, … m high, …`. The ground, road and parking-area layers, triggers and the mover's own colliders don't count. For the player, static scenery doesn't count either (a collider with no Rigidbody and no `NavMeshObstacle`): the landing point is on the NavMesh, which is built round anything a person can't walk through (live session 6: `BridgeMiddleRoadColliders` on StreetProps, which keep traffic out of the middle of the road under the bridge, refused a player at x -1515, z -1150). Vehicles, people, bodies and carving obstacles (the mod's bay props) still count; a trigger on the parked-car or traffic layers does (the game's own check for cars under a placed vehicle includes them). For a vehicle the parked cars within 15 m are also tested by their footprints (each lane car's mesh bounds, turned with the car; Core `Footprint.Overlap`), and so is the building's delivery-job van, shown or hidden: the game hides it while something blocks its stall and shows it again later whatever stands there. Live session 4 put a truck with `clear` inside a white van in a perpendicular stall at industry-city; the collider test alone had passed. A hidden van refuses as `the building's delivery-job van (<name>, hidden now; the game shows it again in its stall)`; `clear` doesn't remove it. A car counts only when its height span (its mesh bounds) overlaps the vehicle's, from 0.3 m above the ground to its roof, so a car on another parking level doesn't. Things found are told apart by the object itself, not by name (pooled cars of one model share a name). The vans are looked up once per command. After a vehicle moves, the bridge tests again where the game put it: the reply's `in_the_way_after` lists anything there (normally empty). Something standing there logs `ERROR: Test bridge: <type> <id> stands in something after the move: ….`; a hidden delivery-job van only logs `Test bridge: <type> <id> stands where a hidden delivery-job van has its stall (hidden): ….` (nothing stands there now, but the game shows the van again later). Anything else refuses the move: `Something stands at x …, z …: <what>.`, naming each thing (`a parked car (<name>)`, `the player's <type> <id>`, `the player`, `a person (<name>)`, else its object and layer). With `"clear": true` the lanes' own parked cars there are sent back to their pool as `BayParking` does (logged `Test bridge: cleared … at …`) and the move goes ahead; anything else (the player's vehicles, people, props, traffic) still refuses.

**`commissary bay_candidates`.** For a commissary whose automatic bay search found nothing (the log's `Commissary <site>: no bay this load …` line), this lists where a truck could stand instead. **`shoot`.** The camera copies the game camera's settings and HDRP camera data, renders 8 frames into its own texture, then the PNG is written and the camera removed. The game changes buildings for its own camera, and the bridge undoes that for each frame of its camera and puts it back in the same frame, before the game's camera renders: the player's view is unchanged. Live sessions 3 to 6 saw facades as a pale see-through copy with a flat white-edged cut over everything in front (the player, the truck). The cause is the game's view-blocking fade (`ViewBlockingObjectManager` on the game's main camera; research note of 13 October 2026, `build/review-modround/ghost-research.md`). Every building, tree or bridge between the game's top-down camera and the player goes into camera-block mode: its renderers get `_Reveal` towards 0 (the ghost), hidden renderers go shadows-only, signs switch off and the building's bottom plane shows (the cut line). That is renderer state, so any camera sees it, and it came and went with where the player stood relative to the game's camera. For the bridge's frame (`TestBridgeUncover`):

- for each entity in the game's active list, at renderer level only: `_Reveal` is set to 1 in a copy of each faded renderer's property block; a blocked entity's hidden renderers (`renderersToHide`, its signs) are shown again (shadows-only back to casting, a disabled one enabled), and its bottom plane's renderers are disabled. Each renderer's exact property block, enabled flag and shadow mode is saved before anything changes and written back, each on its own. The building's logical block state, its layers and object activation are never touched (review round 10: the game's own toggles flip the flag first and `SetActive` objects, which can't be undone exactly), so the entity's `objectsToDisable` stay hidden in the shot;
- the hovered or highlighted building (live session 9: the game's idle cursor over 22 1st Street opened its card and drew it pale with a white edge, and the bridge's shot copied it): the building under the mouse (`CurrentBuildingHighlighted`, `MouseController.currentTargetEntity`), the one whose card is open (`BuildingResume.TargetController`) and any with a map-filter highlight colour. Their root, parts, LOD, ground plane and billboards go from `BuildingsOutlined` to the Buildings layer, and `_SelectionColor` is cleared in a copy of the property blocks of their `renderersToHide` and LOD; all saved first and written back exactly. The reply's `hovered` lists them (`<name> (under the mouse, its building card open, N objects outlined, selection colour)`), `asis_hovered` with `compare`;
- every object on the hover/map-filter outline layers (`BuildingsOutlined` for buildings within 250 m, `InteractiveItemsOutlined` for items) is moved to its plain layer and back to the exact layer it had;
- the game's BuildingHider globals (`GlobalPlayerPos`, `_PO_Height`, `_PO_Height_Offset`) are moved out of reach and back, as since 407e9a4; they weren't the ghost's cause, but the override costs nothing and is undone in the frame.

Each step is undone on its own in a `finally`, in reverse order, so one failure leaves nothing else changed. The reply's `uncovered` lists the entities lifted (`<name> (<type>, reveal 0.00, blocking the game's camera)`) and `outlined` the buildings and items whose outline was lifted; the shot's log line adds `; uncovered …; outline lifted from …`. `"compare": true` renders four more frames as the game has them, nothing undone, and writes `<name>-asis.png` (`asis_path`, with `asis_uncovered` and `asis_outlined` saying what would have been lifted then): the ghost in the as-is picture and not in the shot shows the cause. `state.view_blocked` lists what the game fades now and `state.game_camera` where its camera stands (`x`, `y`, `z`, `yaw`, `pitch`), so a check can stand the player where a building comes between them. A failed frame releases the shot's camera and texture (the pump now runs a failed call's cleanup too). `frames` (a whole number from 8 to 240, default 8) sets how many frames the camera renders before the picture is read; with the game in the background at a low frame rate, 240 frames can outlast the call's `timeout_s`, and the shot then comes back through its op id. `"game_view": true` also saves the game's own frame for that moment, with its camera and UI (`ScreenCapture`, at the end of the frame), as `<name>-game.png` (`game_path`, or `game_error` when the capture failed): ground truth for what the player sees, for example whether a truck that is black in a rain shot is black in the game too. `fov` defaults to 60. Vehicle poses use the truck's hatch (on its right, at the player's place behind it) or the cart's queue side; `bay-pavement` stands 6 m from the bay on its pavement side; `bay-road` stands on the driving lane nearest the bay, 12 m back along it, 1.5 m up, looking at the bay's middle (without traffic lanes, 12 m along and 5 m out from the bay); `door` stands 6 m along the walk from the entrance to the street (as `commissary:`), at eye height, looking at the entrance.

A named pose never starts inside geometry (live session 4: `vehicle-side` inside the facade where the pavement is under 6 m wide, `door` nearly black where the walk is cut off). Each pose has a list of ways round its subject, its own first; for each, a 0.25 m sphere is swept from the subject out towards the camera, and the first solid thing on the line (buildings, walls, roofs, large props; not the subject, people, vehicles, triggers, or things under 0.8 m across such as poles and signs) pulls the camera in to 0.4 m in front of it (Core `ShotClearance`). A way whose room falls below the pose's nearest distance, or whose camera place is inside anything (poles and vehicles included), is skipped. Ways, in order: `vehicle-side` the hatch side 6 m out, from above it (4 m out, 4.5 m up), the other side, from high above (9 m up), nearest 3 m; `hatch-pavement` nearest 1.2 m; `hatch-close` and `cart-counter` 0.8 m; `vehicle-overhead` from above behind, then straight above, 5 m; `queue` along the pavement, then from 4.5 m up, 4 m; `bay-pavement` the pavement, above it, the road side, 2.5 m; `bay-road` the lane behind, the lane ahead, above the lane, 4 m. `door` tries the walk first; if that isn't clear for its full 6 m it weighs every way out (towards the nearest lane and straight out, each turned 0, ±30 and ±60 degrees, at eye height and 3.5 m up) and takes the one with the most room, at least 2 m. The reply's `pose_note` is null when the pose's own way stood clear, else says what changed (`from the hatch side was blocked; taken from the other side`, `…, pulled in to 3.6 m in front of <object> (layer …)`); the shot's log line carries the same note in brackets. With no way clear the pose's own is used and the note says so. A free camera stands where it is put, and `pose_note` warns when that is inside something solid. `camera` gives where the camera stood and its angles. `fov` is 5 to 120 degrees.

**`save`.** `GameManager.SaveGame(name)`, as the pause menu's Save. The reply comes when the game's save threads are done, and only if the save worked. With the bridge on, finalizers on `SaveGameSerializationHelper.SerializeJsonData`, `SerializeBinaryData` and `CompressBinaryData` (logged `Patch SaveGameSerializationHelper.…, test bridge save: Active.`) record what each returned for this save's paths (the game's temp file and the save file): both must return true. Any of the game's failure lines (`Save game serialization failed`, `SaveGame serialization failed`, `SaveGame compression failed`) also fails it, and so does a file in the character's folder that is missing, older than the call or empty. If a finalizer isn't active, the lines and the file decide. Reply `{ "name", "path", "bytes" }`.

**`load`.** From the city it is refused unless the loaded save's name starts with FT too, since leaving skips the game's unsaved-changes question. A second load while one is pending is refused. Progress is in `state.load` and `/health`'s `load`: `pending` from the call, `done` once the city is up with that save and the mod has attached to it since the call (so reloading the same name doesn't count the old city), `failed` with `error` when the game reports a broken save or nothing arrives within 300 seconds. Log lines `Test bridge: load '<name>' done: day D, the mod's save data attached.` or `Test bridge: load '<name>' failed: ….` Finds the newest save of that name in the current version's folder. From the main menu it runs what the Load screen's button runs (`TransitionToSave` then `LoadScene.LoadTransitionToSave`) without its two questions (a save never played with mods, a different mod list). From the city it goes to the main menu first as the pause menu's Main menu does (`LoadScene.LoadMainMenuFromCity`, without asking about unsaved changes), logs `Test bridge: at the main menu; loading '<name>' once its loading screen has gone.` and loads from there.

Both ways wait until no loading screen is left before the menu's load starts, and the way from the city also waits before it leaves for the menu (the city's own screen may still be fading after a load that has just finished). Live session 4 (13 October 2026): a load from the city hung at the main menu twice, with `/health` on `loading` for good. The game's loading screen is a single instance: `LoadScene.LoadScenes` clears `LoadScene.isLoading` before the screen fades out, and the screen removes itself only after its fade (up to 1.6 s). The bridge started the menu's load two frames after the menu came up, inside that fade; the new loading screen met the old one and destroyed itself, its loading coroutine died with it, and `isLoading` stayed true with nothing loading [code, 1.0: LoadScene, LoadingScreen, InstanceBehavior.Awake]. A player never clicks Load that fast.

A load that dies anyway is cleared only when the bridge can show it died. With the bridge on, a postfix on `LoadingScreen.StartLoading` (logged `Patch LoadingScreen.StartLoading, test bridge load: Active.`) notes when the bridge's own pending load starts a loading screen that isn't the game's registered one, which the game then removes: `Test bridge: the bridge's load started a loading screen while another was still up; the game removes the new one, so this load can't run.` Once no loading screen is left, the main menu is loaded and no city is being unloaded, the bridge clears the game's loading flag: `ERROR: Test bridge: the bridge's load died with its loading screen (another was still up); cleared the game's loading flag, so loads work again. the game is at the menu (…).`, and the pending load fails with `the game's load never ran (…): load again`. A loading flag on with no screen for any other reason (the screen's prefab still loading, the pause menu's quit, a load the player started) is never cleared: `load` refuses with `The game's loading flag is on with no loading screen; the bridge can't tell whether a load is still starting, so it leaves the flag alone: wait, or restart the game. the game is at …`, and a pending load times out after 300 s with the same description. Every failed load's error ends with where the game is: `the game is at the <menu|loading|city> (its loading flag on|off, a loading screen is up|no loading screen)`. The bridge's runner lives across scenes (`DontDestroyOnLoad`), so its load coroutine carries on through the change to the menu.

**Limits** (from `docs/test-bridge-mac-review.md`, kept as they are). A list picker takes two clicks, the option and then the game's confirm button, whose label only a live `ui list` shows. Map picks, drags and placing items in the world can't be done through `ui`. `ui list` checks canvases, fading and the screen's edges, not scroll masks or windows on top, so a clipped or covered control can still be listed; list again after any change before clicking by id.

**`new_game`.** Not available: `ok: false`. The game makes a new game's character only in the character creator's screens (`MainMenuController.StartNewGame`, then the Intro scene sets the character and the save name), which the bridge can't fill in reliably. Start a game by hand once, save it under an FT name and use `load`.

**`quit`.** Replies, then half a second later waits for any save being written and calls `Application.Quit`.

**`state`.** As above, with these readings:

- `clock`, `money`, `player`, `licence`, `commissary`, `ledger_today` are null outside the city; `licence` and the rest are null while the mod's save data isn't loaded.
- `player.carrying` is the item name in the player's hands. `player.activity` is `driving` (in a truck or car), `pushing` (a cart or hand truck), `starting` (from Open until the hatch's activity panel runs), `at_hatch`, `walking` (a walk the game runs to a goal: enter, back to the hatch) or `on_foot`. `player.clock_held_by` is null, `time skip`, or the open screens that hold the clock (`phone`, `map`, `call`, `activity panel`, `pause menu`, `confirmation`, `warning`; `a screen` when none of those is known).
- `licence.until_day` is null without a licence; `permits` counts vehicles with a permit; `course_done` is the game's diploma check for the Food Safety course.
- A vehicle's `name` is its type's name; `heading` is null when it isn't on the map. For a truck the player drives, `legal` is the vehicle panel's live reading (`vehicleInfo.currentParkingState`, the one Open checks) and `legal_reason` reads `panel's live reading: Legal|Illegal|NotAvailable`; for any other truck it is the game's own wheel parking test (`Legality.VehicleLegallyParked`), `legal_reason` starting `wheel parking test:`; for a cart it is the mod's pavement rule (`Legality.Check`), `legal_reason` starting `pavement rule:`.
- `hatch_side` is `right` for a truck (where its hatch is); for a cart it is the side its queue formed on, null while no line is laid out. `hatch_to_pavement` is the mod's hatch check for a truck, null for a cart.
- `serving` is `player` when the sales tick counts the player at the window, `crew` when a crew member serves, else `nobody` (always `nobody` when closed).
- `pieces[].item` is the equipment id from the demand tables. `stock[]` lists the cargo that isn't equipment: `item` the game's name, `key` the item key.
- `queue` is null while closed. `length` is Core's customers at the window and in line; `places` are the spots the visible line uses (empty while it isn't shown), `occupied` for the first `length` of them.
- `commissary` is null unless the vehicle has a space or stands in a bay; `site` is its space, `in_bay` whether it stands in any bay (legally parked for a truck, within the radius and on the door's side of the street, as the mod's own test: `Commissary.InBay`), `bay_site` which one.
- `parking` is what the game's hourly parking charge reads for the vehicle when nobody drives it (`ParkingSimulator.RunHourly`): its stored `state` (`Legal`, `Illegal`, `NotAvailable`), the `neighbourhood` it was left in, that neighbourhood's `hourly_price` (null when the neighbourhood is unknown) and the `unpaid` amount the game bills at midnight.
- `route.next` is a line of text, "stop N, HH:MM to HH:MM at x …, z …", for the first stop still to close today.
- `commissary.orders[]` adds `item` and `units`; `total` is goods plus fee (0 while the order waits: the delivery's flat fee is set when it arrives). `commissary.stock[]` adds `key`. `unpaid` sums the rent and fines the game refused.
- `commissary.bays` has every commissary: `resolved` with the bay's first point and the building's entrance nearest it, `failed` when the search found no legal parking (a stored failure is searched again once on every load, and stays `failed` until a search finds a bay), `pending` until the city's parking lanes let it search. `shoot`'s `door` pose and `teleport`'s `commissary:` use that entrance.
- `transactions_today` is the game's transactions of today and yesterday, oldest first; `label` is the transaction type resolved with its data, as close to the bank app's text as the bridge can read it.
- `employees` are the hires the crew dropdown offers (hired, without a building or vehicle), best customer service first.
- `load` is null before the first `load` call.
- `ledger_today.street_food` is today's street food revenue in the mod's ledger; `crew_waiting` is the crew's takings not yet paid in.

## Scenarios

A scenario is a JSON file in `tests/game/scenarios/`. `tools/scenario run <file>` runs its steps in order and stops at the first failed check unless the step says `"soft": true`. Reports go to `build/scenarios/<name>-<time>/` (`report.md`, `report.json`, `events.jsonl`, and the shots fetched from the PC).

```json
{
  "name": "commissary-pay-on-delivery",
  "checks": "CHECKS.md, Commissary look and payment (0.9.10), rows 1 to 3",
  "needs": { "scene": "city", "save_prefix": "FT" },
  "steps": [
    { "call": "debug", "args": { "action": "spawn truck" } },
    { "call": "money", "args": { "set": 20000 } },
    { "remember": "money", "from": "state", "path": "money" },
    { "wait_event": "Commissary order \\d+: 2 boxes", "timeout_s": 30 },
    { "expect": "state", "path": "money", "equals": "$money" },
    { "call": "time", "args": { "run_until": { "day": "+1", "time": "08:05" }, "speed": 20 } },
    { "wait_state": "clock.time", "equals": "08:05", "timeout_s": 300 },
    { "expect": "state", "path": "commissary.orders", "length": 0 },
    { "shoot": { "name": "bay-day", "pose": "bay-pavement", "target": "bay:hells-kitchen" } },
    { "note": "Rows 6 to 9 need eyes: see the contact sheet." }
  ]
}
```

Step kinds: `call` (with optional `expect_ok: false`), `remember` (a value into `$name`), `expect` (`equals`, `not_equals`, `less`, `greater`, `length`, `contains`, `matches` on a dotted path of `state` or of the last call's result), `wait_event` (a regex over new events), `wait_state` (poll `state` until a path meets the condition), `no_event` (a regex that must not appear between two steps), `shoot`, `sleep_s` (real seconds), `note`. Paths are dotted with list indexes (`vehicles.0.stock.1.amount`) and filters (`vehicles[kind=truck].legal`).

## Log checks

`tests/game/logchecks/<version>.txt` holds a build's expected log lines, one per line:

```
# id | rule | regex
patch.runDaily | must | Patch BusinessHelper\.RunDaily: Active\.
crew.paidIn | must | Crew sales paid in: .+, day \d+: \d+ items
no.notActive | never | Patch .+: Not active
```

Rules: `must` (at least once), `never`, `count=N`, `count>=N`, `order` (the regexes listed on one line separated by ` >> ` appear in that order). `tools/check-log <Player.log> [<version>]` also always reports every `Patch …: Active.` and `Not active` line, every mod error line and every exception that names a FoodTrucks type, and exits non-zero on any failed `must`, `never` or `count` rule. Without a version it takes the version from the log's `Version … loading.` line.

`ft shoot` takes a named pose (`--pose` and `--target`) or a free camera: `--at X,Y,Z` with `--look-at X,Y,Z` or `--yaw`/`--pitch` (degrees; yaw clockwise from +z, pitch down), and `--fov`, `--width`, `--height` for either; `--timeout` (default 20 s) is the call's `timeout_s`. `--compare` and `--game-view` pass `compare` and `game_view`; with `--fetch` the extra pictures come too (`result.local_asis_path`, `result.local_game_path`). `--fetch` copies the PNG and needs `BA_GAME_HOST` when the game runs on another PC; the local copy's path is `result.local_path` in `--json` output (and `local_path` at the top, as before). MCP `ft_shoot` takes the same free camera as `x`, `y`, `z` with `look_at` (an object) or `yaw`/`pitch`, plus `fov` and `timeout_s`.

Values in `key=value` are JSON when possible, otherwise strings. Dots build nested arguments. `--json` before `call` prints the raw reply; after `call` it supplies arguments. `call --raw` also prints the raw reply. `wait-event` watches new events. Event cursors are inclusive: request `since` and later, then use the reply's `next` unchanged. Every health, events and call reply, including operation status results, carries a `session` string that changes each bridge start. The client remembers the first reply's session and sends it as the top-level `expect_session` field on every subsequent `/call`. A mismatch returns `ok: false` with `the bridge restarted (session <new>); reconnect first.` and the new session; the command is not run. The client detects a changed session even if the new event counter has already passed the old cursor, then blocks further calls locally until reconnect. An active scenario fails immediately, including soft steps and `--keep-going`, and clears remembered values; events and remembered values from before the restart are void. Start a fresh scenario run. `ft events --follow` announces a restart on stderr and resumes from event 1 in the new session. A lower `next` than the cursor remains an additional restart check.

`open`, `exit`, `restock` and `rent_bay` require driving the truck or pushing the cart. Teleport the player beside it, unpause with `time pause=false`, call `vehicle enter`, and wait for `state.player.in_vehicle` to match its id. Keep time unpaused through entry and hatch walks and their completion waits. Unpause before `open` or `exit`. Check each vehicle reply's `done`. After `open` or `back_to_hatch`, wait for `player.activity: "at_hatch"` and the matching `player.at_hatch` for a truck. Enter replies can report done when the walk starts; wait for activity driving/pushing and the matching in_vehicle. Player teleport cancels pending navigation, including entry and hatch-return walks. Close an open vehicle before teleporting it. Panel refusals for `restock` and `rent_bay` return `ok: true, done: false` with any notices and `why` for a missing/refused choice (`why` is null otherwise). Calling a panel operation while not driving/pushing remains a failed call.

Speed is above 0 and at most 60. The bridge handles `run_until.day: "+N"`, then pauses and restores speed 1. `expect` and `remember` read `state` or `result` (the last call's result). Every normal command reply carries an `op` id, also shown by readable `ft call` output and in MCP results/errors. `ft op N` and MCP `ft_op` query it without creating another operation. `timeout_s` is clamped to 1..600 seconds by both client and bridge. `.mcp.json` registers the stdio server as `foodtrucks-game`. It uses the same environment variables and fetches screenshots into `build/shots/`.
