# Test bridge

Tooling that lets an agent drive and read the game on the Windows PC without Peter's hands. Built 12 October 2026 after the 0.9.8 agent run, where Peter had to walk, drive and click world objects for the agent, notices faded before the agent could read them, and the clock kept running while the agent worked.

The pieces:

| Piece | Where | What it does |
|---|---|---|
| Notice log | `unity/FoodTrucks/Scripts/` | Every notice and phone text the mod shows is also a `Notice:` or `Phone:` line in `Player.log` |
| Test bridge | `unity/FoodTrucks/Scripts/TestBridge*.cs` | HTTP on `127.0.0.1:8330` inside the game, only when the game was launched with `-foodtrucks-test` |
| `tools/ft` | Mac | Command-line client for the bridge |
| `tools/ft-mcp` | Mac | The same calls as an MCP server (stdio), registered in `.mcp.json` |
| `tools/mock-bridge` | Mac | A fake bridge with canned state, for working on the client and scenarios without the game |
| `tools/scenario` | Mac | Runs a scenario file (steps and checks) against the bridge, writes a report |
| `tools/check-log` | Mac | Checks a `Player.log` against a build's expected log lines |
| `tools/contact-sheet` | Mac | One HTML page of the screenshots a run took |
| `tools/run-remote.sh` | Mac → homepc | Starts the game in Peter's desktop session with the test flags, opens the ssh tunnel, stops the game |
| Soak test | `tests/` | Many simulated days through Core with seeded random play, checking invariants |

## Safety

- The bridge starts only with `-foodtrucks-test` on the game's command line. Without it nothing listens, and the Workshop build behaves as before.
- `POST /call` requires `Content-Type: application/json` and refuses `Origin` or `Sec-Fetch-Site` headers before queuing any operation. Use the native CLI/MCP clients; browser-origin requests are refused even from a localhost page.
- It binds `127.0.0.1` only. The Mac reaches it through `ssh -L 8330:127.0.0.1:8330 homepc` (`tools/run-remote.sh tunnel`).
- Commands that change a save (money, spawns, time jumps, debug actions) are for throwaway **FT** saves only. `load` and `new_game` refuse any save whose name doesn't start with `FT`, and the bridge refuses every changing command while the loaded save's name doesn't start with `FT`.


### Sharing the game PC

The normal game (`8330`, instance `normal`), Windows test rig (`18330`, instance `agent1`) and local Mac fallback (`28330`, instance `agentmac`) use the same commands and **separate ownership locks**. The server enforces ownership on every changing command, including UI clicks, console/debug commands, load, save, quit and screenshots. Health, events, state, operation status, parks, places, map, day summaries, UI list/tree/geometry and the rig's `mouse status` remain readable without ownership.

The Mac fallback is manually launched when the PC is unavailable. It needs no tunnel: see [the Mac agent workflow](https://github.com/PeterHartwieg/big-ambitions-agent-rig/blob/main/docs/MAC.md) (sibling checkout `../big-ambitions-agent-rig/docs/MAC.md`) for local start/stop/ownership commands. The Windows commands below do not manage it.

Choose a unique owner for each agent/session. From this repository:

```sh
export BA_GAME_HOST=homepc
export BA_LOCK_OWNER="my-project-my-session"
python3 tools/bridge-lock setup
python3 tools/bridge-lock acquire --instance normal --purpose "My disposable test"
tools/run-remote.sh start
# Commands and scenarios automatically use this owner's token.
tools/ft call time pause=true
python3 tools/bridge-lock release --instance normal
```

For the agent rig, use `--instance agent1`, set `BA_BRIDGE_URL=http://127.0.0.1:18330`, and open its tunnel. The rig's `agent lock acquire|status|release` is equivalent. Do not use the normal-game launcher to start the rig. MCP has `ft_lock` (`op: status|acquire|release`, `owner`, optional `purpose`); `ft_call` with `cmd: lock` also works. Online CLI acquisition: `tools/ft call lock op=acquire owner=my-session`. Set `BA_LOCK_OWNER` consistently between independent CLI invocations. Each persistent MCP client retains its chosen owner.

Ownership uses random per-instance tokens, stored locally with mode 0600 under `~/.big-ambitions-bridge/client-tokens/`; `BA_LOCK_TOKEN` can supply a token directly. The Windows lock stores its SHA-256 hash, owner, purpose and pending work under `%USERPROFILE%\.big-ambitions-bridge\<instance>`. A matching owner label alone cannot take over. These are coordination locks between trusted local tools, not an OS security boundary.

There is **no automatic expiry**. Release explicitly when work is finished; pause the city first. Queued/deferred calls retain reservations through actual completion, even after HTTP timeout. Loads, accelerated time, drives, quitting and a simulation the owner left running also retain ownership. A crashed process's pending work is pruned using PID plus creation time, but its ownership remains recoverable with the original token. Do not delete lock files to recover an unknown owner; coordinate an explicit handoff. An owner can use the verified launcher's forced stop to terminate its own wedged test process; this cancels work and may lose unsaved test progress.

Launch, stop, install and park/restore tools share this store and reject unauthorized lifecycle changes even while a bridge is offline. Normal-game and agent operations do not block each other. Older `game-lock.txt` reservations block normal-game takeover until their holder or Peter explicitly releases them. The old owner-prefix and `DR_IGNORE_LOCK` bypasses are removed. `run-remote.sh lock [minutes] [purpose]` remains a compatibility entry point, but minutes no longer expire ownership.

Raw HTTP clients must send `lock_token` at the **top level** of `/call`, plus `expect_session` from `/health` for changing commands. Never put a token in `args`. Manage ownership with `{"cmd":"lock","args":{"op":"acquire","owner":"my-session","purpose":"test"},"lock_token":"<random-token-at-least-32-characters>"}`. Status and release use `op: status` and `op: release`; release requires the same token. `/health` advertises `lock_protocol: 1`, `control_process_pid`, and a public `control_lock` status without token/hash disclosure.

## Local release-candidate packaging

After the normal build, `python3 tools/package-release.py` validates the existing package and SHA-256 manifest and creates `build/FoodTrucks-0.9.10-rc.zip`. `--source`, `--manifest` and `--output` override those paths. The command performs no build, download, upload or publication and leaves the mod's unreleased version unchanged.

The archive contains one `FoodTrucks/` folder with the runtime mod/Core/Harmony assemblies, Windows and Mac bundles, tuning data, locales, README and both project and Harmony license notices. An explicit runtime allowlist refuses game assemblies, save files, source code and any other unexpected input even if listed in the checksum manifest. Integrity checks require the exact manifested file set and reject duplicate/unsafe paths and symlinks. File bytes are checked while streaming into the ZIP; the source is checked again before retaining the archive.

Entries have sorted paths, fixed timestamps and permissions. Identical package bytes produce identical archives with the same Python/zlib runtime regardless of source timestamps or permissions. The output is created atomically without replacing an existing candidate and without duplicating the temporary ZIP's disk allocation. No real release archive was generated during the low-disk session; temporary-fixture packaging tests passed. Packaging does not establish gameplay QA or publication approval.

## Transport

All bodies are UTF-8 JSON. Every reply has `ok` and, next to it, `session`: 8 hex characters the bridge picks at random each time it starts. A different `session` means the game or the mod restarted, and nothing a client knew from before (operation numbers, event numbers, state) holds. A `/call` body may carry `"expect_session": "<8 hex>"`; when it differs from the current session the call is refused before it is numbered or queued: `{ "ok": false, "session": "<current>", "error": "the bridge restarted (session <current>); reconnect first." }`. A failed call has `ok: false` and `error` (one sentence a person can act on).

### `GET /health`

Answered on the HTTP thread from values the main thread refreshes every frame, so it works while the game loads.

```json
{ "ok": true, "session": "3f9a1c07", "mod_version": "0.9.10", "bridge_version": 1, "scene": "menu|loading|city", "save": "FT bridge", "day": 3, "time": "14:05", "paused": false, "time_skip": false, "frame": 123456, "load": { "name": "FT bridge", "status": "pending|done|failed" } }
```

### `POST /call`

```json
{ "cmd": "state", "args": { } }
```

Runs on the Unity main thread, one call after another. The HTTP thread waits up to `timeout_s` (default 10, an `args` field) for the result; past that the reply is `ok: false, error: "timed out on the main thread; …"` and the command still finishes in the game. Reply: `{ "ok": true, "op": 17, "result": { … } }`, or `{ "ok": false, "op": 17, "error": "…" }`.

Every call gets an operation number `op`. `{ "cmd": "op", "args": { "id": 17 } }` answers at once, whatever the main thread is doing, with `{ "ok": true, "result": { "id": 17, "cmd": "save", "session": "3f9a1c07", "status": "pending|done|failed", "result": { … }, "error": "…" } }` (`result` only when done, `error` only when failed). After a timeout, ask this instead of sending the call again. The bridge keeps every pending operation and the last 500 completed operations, ordered by completion.

Each request is served on its own thread, so `/health`, `/events` and `op` answer while a `/call` waits.

### `GET /events?since=N`

The bridge keeps the last 2,000 events in a ring buffer: every line the mod logs (`Log.Info`, `Log.Error`), every notice and phone text, and Unity errors and exceptions from any source. Reply:

```json
{ "ok": true, "next": 812, "dropped": 0, "events": [ { "seq": 811, "real": "2026-10-12T14:03:11.204Z", "day": 3, "time": "14:05", "kind": "log|error|notice|phone|unity_error", "text": "…" } ] }
```

`next` is the `since` to pass next time. `dropped` counts events that fell out of the buffer between `since` and the oldest kept.

An event's `day` and `time` are the game clock when the line was written: read directly when the line comes from the main thread in the city, else the clock of the frame's `/health` snapshot. `/health` and the stamps read the same clock, so a stamp that differs from a later `/health` means the clock moved in between. The bridge logs any jump of more than 30 game minutes in one frame, once the jump has settled: `Test bridge: the clock jumped from day 1 08:44 to day 1 11:47 in one go: <why>.`, where `<why>` is `a time skip (sleep or a paid activity)`, `the player collapsed (hospital)` or `something set the time (the game, a load or another mod)`. Live session 4 saw `load 'FT bridge' done` stamped 08:44 and `/health` say 11:47 seconds later; the stamps and `/health` already shared one clock then, so the clock itself jumped (cause not seen; the jump line names it next time). `time_skip` in `/health` is true while the game's time skip runs.

## Building entry and carried bags

Issue 34, blind run 3 (17 October 2026): **source checked in the read-only 1.0 decompile; pending in game**. A paid paper bag containing five banana bags did not enter the player's rented home at `ba:street_thirdstreet#9`. The old `handled: false` reply cannot establish which guard rejected that historical click.

The source trace is `MouseController.Run` → `CityBuildingController.OnIoLeftClick` → `EntityController.OnIoLeftClick` → `WalkOverAndInteract` → `PlayerController.SetGoal` → virtual `CityBuildingController.Interact` → `BuildingManager.EnterBuilding`. `BuildingEntranceDoor` is door data (transform, ID, always-open flag), not a separate clickable controller. `BuildingHelper.CanEnterBuilding` accepts a player-rented building regardless of business hours. `Interact` then checks mission delivery, access/hours (or a nearby always-open door), DLC, goals, installation and entrance fee, and selects the nearest door ID. None checks paper bags, shopping bags/baskets, boxes, held cargo or its paid flags. `PlayerController.InitHoldingItem` / `RestoreItemInHandsAfterEnteringBuilding` explicitly restore the held-item panel when loading into a building. By contrast, `ExitZoneDespawner.OnTriggerEnter` refuses unpaid cargo and removes an empty `cannottakeoutside` container on leaving; those are not home-entry rules.

The bridge did have a pointer-dependent defect: `CityBuildingController.OnIoLeftClick` immediately returns false if `EventSystem.current.IsPointerOverGameObject()` or `FullMenu.IsOpen`. An ID click never moves the physical pointer. A pointer parked over the hands HUD can therefore swallow it, even though the target ID is a door. `UseBuildingClick` now refreshes native targets, checks the same navigation/minigame guards, interacts immediately only within native reach, or starts `MoveTowardsEntity` and calls virtual `Interact` on arrival. A failed route requests the game's own cannot-reach notice. Phone/map clicks refuse with a close-screen hint. No direct entry, teleport, cargo mutation, navigation-blocker clearing or new Harmony patch is involved. Remaining native entry failures and walks/loads still pending after 120 seconds return `why`, `still_walking` and `still_entering`; `tools/play use` prints the reason and notices instead of "nothing happened". `handled` still means the interaction was dispatched, not that entry succeeded.

The click's scoped `UseNoticeCapture` subscribes to `UI.Notification.Notifications.onShow` and resolves the same key/data as `NotificationsUI.ShowNotification`. The old `Notices.BeginCapture` only captured calls through the mod's wrapper, losing vanilla refusals. Both native and mod notices now appear once in the click reply; its `why` prefers the last error over unrelated informational notices. The subscription is removed on completion, exception or deferred-command cleanup, without changing the notification UI or its other listeners.

`TestBridgeHands.RequireCarryControl` checks activity/transition/navigation state, not empty hands. `pickup` reuses `UseClick` for a placed container; the hand-truck controls use the native storage/Park/cargo buttons. No general pocket/stow inventory control was found in `PlayerHelper`, `PlayerController` or `ItemPanelUI`, and entry does not need one. Existing `drop` works in editable interiors; `handtruck load` handles paid cargo through native storage. Neither is required to enter home with a bag. All Food Trucks Harmony registrations are in `Patches`: none targets building clicks, building/door entry, `CanEnterBuilding`, player navigation or held-item access checks. The held-item panel postfix only hides the mod's vehicle button.

`tools/mock-bridge` mirrors the reply fields and building refusal cases; the balance calculator has no building-entry/carrying model and needs no change. ## Floor plan controls

Built, not yet run in game (17 October 2026). Geometry only: these controls do not choose or suggest layouts, show prices/balance values, grant furniture, or expose another building's layout. `tools/play floorplan` prints the plan with one character per square, column headers (A…Z, AA…), numbered rows, a legend, then one line per item: ID/name, covered squares, actual yaw, each use square and its reachability. `@` marks the player; `.` floor, `#` wall, `=` known exit door/opening, `X` blocked, blank void, letters/digits items, `*` overlapping item footprints. Item labels omit reserved `X`; the list retains every item if labels run out. Structured `cells` preserve the ground classification under item/player overlays. Columns go toward world +X (right); rows go toward world +Z (up in the printed map). No floor selector: stand on the desired floor.

**Grid facts (source evidence, not a visual check).** `BigAmbitions.PlacementSystem.BuildingGrid` and `BuildingGridWithDifferentHeights` control the ground/wall grid visuals. `BuildingGridBase.GetGroundGrids` returns the actual `GroundGrid` collider set; `GroundGrid` also carries roof/car permissions. These classes do not define a separate local placement lattice or per-building square size. `BigAmbitions.Items.Item.gridSize` defaults to **0.5 world metres**. `PlacementSystem.UpdateGroundItemPosition` snaps world coordinates through `Extensions.MathHelper.RoundVectorToNextValue` using that item's `gridSize`, then restores the hit's Y. The helper delegates to `RoundToNextValue`: `floor(value / step + 0.5) * step`. The MathHelper body was additionally read from the local `HGExtensions.dll`, since it is outside the supplied decompile's assemblies. Asset-specific grid overrides are still possible; the bridge returns the actual native result rather than promising every item uses the default. Absolute rotation retains the existing nearest native `degreesPerRotation` step, with the existing 45° fallback; replies report final transform yaw.

The plan uses this **0.5 m world lattice**, not an arbitrary resampling size or a rotated building-local lattice. A square is centred on an allowed base-grid anchor and spans ±0.25 m on X/Z; boundaries map toward +X/+Z using the native rounding rule. `origin` is the world centre of A1. For zero-based column `c` and one-based row `r`, `x = origin.x + c * 0.5`, `z = origin.z + (r - 1) * 0.5`; Y comes from the current physical floor. Thus C4 resolves to `(origin.x + 1, origin.z + 1.5)`. The item's **anchor**, not a footprint corner, is placed there. Coverage reports every square whose area intersects a projected collision footprint, excluding mere edge contact.

`Buildings.BuildingSizeHelper.GetData` / `BuildingSizeData` provide size identities, versions and wall heights; `BuildingSizeResolver.GetInstantiatedBuilding` selects a size/version's structure via `BuildingSizeContainer`. A size name alone is not a unique geometry: structure version matters. The plan identifies both. Its A1 is aligned to the floor geometry's minimum world X/Z, with one base square of perimeter. Equal structures at the same native grid phase get equal relative labels; origin is always explicit. Physical ground-layer colliders in `BuildingManager.currentBuildingVersion`, plus active colliders registered by `BuildingGridBase.GetGroundGrids`, supply the outline. Hidden grid visuals are never enabled for the survey. Bounds establish only the survey extent, never fill a rectangle as floor. Each square's anchor is ray-tested against actual current-height floor colliders, keeping concavities and holes. `MultipleHeightsBuildingController.heightToShowSecondFloor` selects the player's physical floor; `GetItemHeightIndex` filters items. No view floor is changed. Placement verifies the requested and native-snapped anchor on that same physical floor before committing, preventing a long native ray from silently placing on a lower floor.

Geometry is **sampled**: narrow features between samples can be missed. Walls and `GroundUnplacable` volumes are sampled with small overlap boxes; `InteriorElement.placementBlocked` supplies blocked floor surfaces. `ExitZone.door` identifies known openings; arbitrary internal openings without an exit component are ordinary floor, not invented doors. Oriented box colliders give projected box footprints; other collider shapes use explicitly marked conservative bounds. Flat decoration can overlap furniture; covered squares are observation, not a replacement collision rule. Noninteractive items remain in the item list. No backing-wall/stack-slot/finish/blueprint controls are included.

**Use squares and reachability.** Each `items[].use` entry is a cached `EntityController.navMeshTargets` transform, including world X/Y/Z, square (null outside the survey), wall test and path status. Per-target checks follow `EntityController.GetClosestNavMeshTargetPosition`: `PathHelper.IsThereAWallBetweenTargetAndEntity`, `NavMesh.CalculatePath` with `PlayerController.navMeshQueryFilter`, complete paths or partial paths ending within 0.5 m. Item `reachable` calls the native method itself (`Vector3.zero` means none). Empty use lists do not invent a stand point. The read-only survey does not reposition/refresh targets. Placement/check calls `UpdateNavMeshTargets` at the candidate and performs the same reach test. These are immediate observations on the current NavMesh; navigation obstacles may settle on later frames, so actual walking/interaction still needs an in-game check.

**Placement/check lifecycle.** `tools/play place C4 [--rotation DEG] [--move NAME] [--check]` and `place X Z …` share `PlaceHeld`. Normal save/session/operation-ID guards and the client's STOP-file rule apply to checks too, because a temporary native placement occurs. Explicit grid snapping is set and restored; commands refuse while physical rotation input is active. Both paths capture `PlacementValidation.CurrentOverlappingCollider` on overlap failure (localized item name or collider name). `fits` reports native geometric validity, separately from `reachable`. A blocked surface can reject before the ghost moves: `position_resolved: false` then identifies the returned requested anchor, and reachability stays null rather than testing the old ghost pose. A check always cancels instead of saving. New furniture returns through the game's cargo cancellation; moves use native `RevertPlacement`. Cleanup also runs on exceptions; temporary nav-target caches and the prior snap flag are restored. `restored` compares cargo (including paid state, colours and nested contents), the item-ID set, instance/transform poses, parents and attachment entries; false is reported explicitly rather than claiming the furniture is back. Internal snapshot prices are compared but never returned. These postconditions are evidence for the observed state, not a proof of every native callback's effects. Check returns `placed: false`, `checked: true`; real success includes the resolved square, actual rotation and reachability. Failed placement leaves the original item through native cancellation.

`tools/mock-bridge` supplies a deliberately fake 6 × 5 m room plus a perimeter, blocked square and hole; it exercises the protocol and rendering, not game physics. `tools/tests/test_floorplan.py` covers survey read-only behavior, mapping/negative ties, real and checked placements/moves, blockers, unreachable targets, conservation, input forms and guards.

Validation: 170 Python tests passed with `FT_TEST_TRANSPORT=inprocess python3 -m unittest discover -s tools/tests`; the final affected floor-plan and playthrough tests also passed. `dotnet test` built the tests but VSTest could not open its socket in the sandbox; an in-process xUnit runner ran the same 1,976 cases with zero failures and one skipped. All runtime scripts passed a temporary C# source-compilation check against local game assemblies. This was not an SDK package build or an in-game check.

## Game side, as built

Built 12 October 2026 in `unity/FoodTrucks/Scripts/` (`Notices.cs`, `TestBridge*.cs`). Not yet run in game; every game call below comes from the 1.0 decompile, and the ones to check first are listed in CHECKS.md, "Test bridge". Where the build differs from the contract above, this section wins.

**Developer actions.** `DebugActions` also requires `-foodtrucks-test` before registering developer console commands, accepting debug hotkeys or running a named bridge action. Without it, the only retained action is the player's safe uninstall step (`Ctrl+Shift+F11` / `foodtrucks_uninstall`), with its existing second confirmation. The bridge's FT-save guard continues to apply to bridge commands.

**Startup.** One line at the mod's initialisation load: `Test bridge: listening on http://127.0.0.1:8330/ (session 3f9a1c07).` or `Test bridge: off (the game was started without -foodtrucks-test).` A taken port logs `Test bridge: could not listen on 127.0.0.1:8330 (…); … The bridge is off.` With the flag the bridge also sets `Application.runInBackground`, so the game keeps running when its window loses the focus. `Test bridge: stopped.` when the mod unloads.

**Collision log.** With the flag, a postfix on NWH's `VehicleController.OnCollisionEnter` logs each collision of a food truck (the cart has no NWH controller) that passes NWH's crash-sound filter (contact points, and any layer but Ground, GroundUnplacable and Roads, as `DamageHandler.IsCollisionValid`), at most one line per 0.25 s for each vehicle and object hit: `Collision (test bridge): truck <id> hit <collider> on <root> (layer <layer>) at x …, y …, z … on the vehicle (x right, z forward), our <collider>; relative speed … m/s, vehicle … km/h; passes NWH's crash-sound filter.` Added 13 October 2026 for the crash sound Peter hears when steering hard (CHECKS D6).

**Notice log.** Every notice the mod shows is a `Notice: <text>` line and every text it sends a `Phone: <contact>: <text>` line, with the text resolved as the game shows it (`LocalizorManager.Localize(key, data)`). A key the game has no text for is logged as `<key> {name=value, …}`. The player's own line in a call (the commissary order read-back) is `Phone: <contact>: [player] <text>`. What the player sees is unchanged.

**FT guard.** `console`, `debug`, `time`, `money`, `teleport`, `walk`, `vehicle`, `commissary`, `crew`, `route`, `fixture`, `floorplan`, `place`, `logistics run`, `save`, `ui click`, `ui escape` and the rig's `mouse` gestures (not `mouse status` or `release`) need the city and a loaded save whose name starts with `FT`. For `ui click` and `ui escape` the refusal reads `ui works only in a loaded FT city; use load from the main menu.` They also refuse when the save's character folder holds a save whose name doesn't start with FT (the game's own `Recover #N` and `Recover Midnight` aside): `This save's character also has saves not starting with FT (<first name>); make FT saves with a character of their own.` `load` checks the same for the save it loads (and, from the city, for the city it leaves). So make FT saves from a new character of their own, never by saving a series city under a new name. `state`, `day_summary`, `places`, `map`, `ui list`, `ui geometry`, `shoot`, `logistics status`, `op` and `quit` work with any save. `load` from the city needs an FT city. `save`, `load` and `new_game` take only names that start with `FT`.

**Scene.** `menu` covers the main menu and the character creator; `loading` covers the loading screen and the step between a save and the city; `city` is the city with a save loaded.

**`/events`.** `since` is the first number wanted: the reply has the events numbered `since` and later, and `next` is the number after the newest. Numbers start at 1. The mod's own error lines arrive once, as `error`, not again as `unity_error`.

**Unload.** Each HTTP server is started under one bridge generation and stamps every request it accepts with it, so a request the old server takes during a stop never counts as the new generation. Taking a call into the main thread's queue and stopping share one lock: a call whose generation has ended by then (a stop, perhaps a start, came in between) is refused with `the bridge stopped`, and the main thread also fails any queued call from an earlier generation instead of running it. When the mod unloads, the bridge stops taking calls, fails every queued and pending call with `the bridge stopped` (a shot's camera and texture are released), and clears its operations, events, run_until and load status, so a start after the mod is enabled again begins clean.

**Error lines.** Every line the mod logs through `Log.Error` starts `ERROR: ` (once), after the game's `[Mod:Food Trucks]` prefix; the `error` events carry the same text.

**Operations.** `timeout_s` is clamped to 1…600 before the call is queued. Every `/call` reply carries `op`, and `{ "cmd": "op", "args": { "id": N } }` gives that call's status (see `POST /call`). Requests are served each on their own thread; the calls still run one after another on the main thread.

**`/call` that finish later.** `save` (until the file is written), `teleport` of the player (until the move out of a building or vehicle ends), `walk` (until the player arrives or stops) and `shoot` (8 frames) answer when they finish, within `timeout_s`. Past it the reply is `timed out on the main thread` and the work still finishes.

**`time`.** `speed` multiplies the player's own game speed from Options (`GameManager.SetMinutesMultiplier`), from above 0 to 60; 1 is normal play. `speed` alone also unpauses. `run_until` takes `day` as a number or `"+N"` (days from today; default today) and `time` as `"HH:MM"`; it runs the clock at `speed` (default 1), checks every frame, and at the time pauses (the game's own pause, `SetPlayerPause`) and sets the speed back to 1. With the bridge on, a Harmony prefix on `GameManager.RunMainGameTick` (logged `Patch GameManager.RunMainGameTick(Single), test bridge run_until: Active.`) keeps any step of the clock from going more than 0.01 of a minute past the target, and the run counts as arrived only once the minute the game shows is the target, so it stops on that minute (its hour's events included, for a target on the hour). Live session 5 stopped once at 16:04 for 16:05: the old check took 16:04.999 as arrived. `state.clock.run_until` is the target while it runs; `state.clock.arrived_at` is where it stopped ("day D HH:MM") until the next `time` call. Anything that unpauses is refused while a screen holds the clock (the phone, the map, a call, an activity, a menu) or a time skip runs. `state.clock.speed` reads the game's multiplier back.

`needs.happiness_modifiers` lists the modifiers the way the phone's Persona app does (`CharacterStats.SetUpHappinessModifiers`): `name` (the type's text), `amount` (the game's percentage; happiness is their sum held to 0 to 100, `HappinessHelper.UpdateHappiness`; null for a type the game doesn't know) and `hours_left`, with `shows_time` false where the game shows no time (-1 or `hideDuration`). `needs.warnings` holds the game's own need warnings: `hungry` and `very_hungry`, `tired`, `exhausted` and `out_of_energy`, at the thresholds of its expressions (`EnergySettings`: low and too low) and at 0 energy.

`keep_needs` (added 13 October 2026 after live session 4, where two game days of `run_until` ended in a collapse, a clock jump to 08:00 the next day and a $2,000 hospital bill): on by default for `run_until`, off for `speed` alone, and given as `true` or `false` on either; a pause turns it off, and so do reaching the `run_until` target and leaving the city. While it is on and the clock runs, whenever energy or hunger falls below 40 (Core `NeedsTopUp`) the bridge tops both up through the game's own needs API (`EnergyHelper.GenerateEnergy`, as a bed or drink adds; `EnergyHelper.SetCurrentHunger`, as eating sets) and logs `Test bridge: needs topped up while the clock runs (energy 39.4 to 100.0, hunger 52.0 to 100.0), day 2 14:05.` The top-ups stop, with `Test bridge: needs top-ups stopped: <why>.`, as soon as the save stops being an FT save of a character with FT saves only (the guard every changing command uses). A `time` call is checked whole before anything changes: a refused call leaves the clock, `run_until` and `keep_needs` as they were. Turn it off (`"keep_needs": false`) to test needs themselves. `state.clock.keep_needs` says whether it is on. Happiness isn't topped up: the game never collapses the player for it, and it rebuilds happiness every hour as the sum of its modifiers (listed as `player.needs.happiness_modifiers`), so a value set by hand wouldn't hold. Low happiness burns energy up to 25% faster and slows its regain, and a hire whose job demands include a minimum player happiness (50 by default) loses satisfaction below it; live session 5 saw happiness fall from 100 to 40 in a two-day run. Whatever the setting, a collapse (the game's hospital flag `EnergyHelper.goingToHospital` rising with energy at the hospital threshold, read every frame; a doctor's visit or surgery sets the same flag with energy to spare and isn't counted) logs `Test bridge: the player collapsed at day D HH:MM (energy …, hunger …, happiness …); the game takes them to hospital, sets the clock to 08:00 and bills the stay.` The game collapses the player when energy reaches its hospital threshold (-20) while on foot and not in a menu; in a vehicle energy keeps falling to -20 and the collapse comes on stepping out [code, 1.0: EnergyHelper.UpdateEnergy, GoToHospitalIsEnabled].

**`money`.** Writes the balance directly. The top bar follows on its next update.

**`teleport`.** For an `x`, `z` move the bridge reads every surface of the game's Ground layer stacked at that point (a street under an elevated road) and takes, with an explicit `y`, the surface nearest it within 1.5 m (for the player, a walkable one); otherwise a walkable one nearest the mover's own height; otherwise the one nearest that height (Core `GroundPick`). Walkable, for the player, means NavMesh of the player's own agent type and areas within the 3 m the landing allows and within 1 m of the surface's height and, while the player stands on the NavMesh within 100 m of the target, a complete walking route from there (longer routes come back partial in the city, so beyond 100 m they aren't checked). The deck at x -1490, z -1150 that live sessions 4 and 6 took for a highway is the game's walkable bridge (`BridgeMiddleRoad`, with NavMesh, a walking route from the street, and people and benches on it), so a `y` of 5.06 there lands on it; a refusal needs ground with no walkable NavMesh, such as x 412, z 200 inside a Hell's Kitchen block. `surface` ends `; walking routes checked from the player's place`, `; walking routes not checked (more than 100 m from the player)` or `; walking routes not checked (the player isn't on the NavMesh)`. A vehicle's surfaces are read with any NavMesh. A player move with no walkable surface at all is refused too, even when it is the only surface there (`No walkable ground at x …, z …: no walkable surface of 1: 5.06 not walkable; …`); a vehicle keeps the fallback. An explicit `y` with no such surface is refused: `No walkable ground at x …, z … near y 5.06: no walkable surface within 1.5 m of the y asked for (5.06); surfaces there: 0.20 walkable.` (`No ground …` for a vehicle). The player's landing must also be within 1 m of the chosen surface's height, so a NavMesh on another level never takes them there. Live session 5: a reply said "nearest the mover's height (0.09) of 2: 3.22, 0.20" and took 3.22 because the street read as not walkable with a 1 m search, and a `y` of 5.06 over a street put the player on the street; the reply now lists each height as walkable or not. Live session 4: the highest surface put the player on the bridge deck at y 5.06 when the street below was meant. The reply's `surface` and a log line say which: `Test bridge: teleport to x -1490.0, z -1150.0: y 0.05, the walkable surface nearest the mover's height (0.10) of 2: 5.06 not walkable, 0.05 walkable.` A vehicle with an explicit `y` and no ground under the point is put at the point as given; the player is refused. The player's navigation is reset first (`PlayerController.ResetNavigation`, which also drops a Back to the hatch walk), then the player goes through the game's `GameManager.SetPlayerPosition` (out of a building or garage first, then a NavMesh warp) after leaving the hatch or the driver's seat, and must land within 3 m of walkable ground. A vehicle goes through `VehicleHelper.TeleportVehicleToGround` and is refused while it is open. Its body's interpolation (NWH sets it on) is off for the move and comes back after the next physics step: with the clock paused, interpolation kept drawing a driven truck between its last two physics poses, partway from the old place to the new one (live session 5).

Before either moves, the bridge tests the place for anything else standing there, from 0.3 m above the ground up: for a vehicle its own footprint, for the player a standing person's capsule. The footprint is the box round its solid colliders' own shapes (a box collider's size, a sphere's or capsule's enclosing box, a mesh's local bounds) carried into the vehicle's frame with their scale (Core `Footprint`), so it is the same whichever way the vehicle faces; the bridge logs it once per vehicle type: `Test bridge: footprint of <type>: … m across, … m long, … m high, …`. The ground, road and parking-area layers, triggers and the mover's own colliders don't count. For the player, static scenery doesn't count either (a collider with no Rigidbody and no `NavMeshObstacle`): the landing point is on the NavMesh, which is built round anything a person can't walk through (live session 6: `BridgeMiddleRoadColliders` on StreetProps, which keep traffic out of the middle of the road under the bridge, refused a player at x -1515, z -1150). Vehicles, people, bodies and carving obstacles (the mod's bay props) still count; a trigger on the parked-car or traffic layers does (the game's own check for cars under a placed vehicle includes them). For a vehicle the parked cars within 15 m are also tested by their footprints (each lane car's mesh bounds, turned with the car; Core `Footprint.Overlap`), and so is the building's delivery-job van, shown or hidden: the game hides it while something blocks its stall and shows it again later whatever stands there. Live session 4 put a truck with `clear` inside a white van in a perpendicular stall at industry-city; the collider test alone had passed. A hidden van refuses as `the building's delivery-job van (<name>, hidden now; the game shows it again in its stall)`; `clear` doesn't remove it. A car counts only when its height span (its mesh bounds) overlaps the vehicle's, from 0.3 m above the ground to its roof, so a car on another parking level doesn't. Things found are told apart by the object itself, not by name (pooled cars of one model share a name). The vans are looked up once per command. After a vehicle moves, the bridge tests again where the game put it: the reply's `in_the_way_after` lists anything there (normally empty). Something standing there logs `ERROR: Test bridge: <type> <id> stands in something after the move: ….`; a hidden delivery-job van only logs `Test bridge: <type> <id> stands where a hidden delivery-job van has its stall (hidden): ….` (nothing stands there now, but the game shows the van again later). Anything else refuses the move: `Something stands at x …, z …: <what>.`, naming each thing (`a parked car (<name>)`, `the player's <type> <id>`, `the player`, `a person (<name>)`, else its object and layer). With `"clear": true` the lanes' own parked cars there are sent back to their pool as `BayParking` does (logged `Test bridge: cleared … at …`) and the move goes ahead; anything else (the player's vehicles, people, props, traffic) still refuses.

After a vehicle moves, its parking state is read again: the game's `CarController.isCheckedForParkingZone` is reset so the game reads it when the car stands still, and if the player drives it `CarController.UpdateParkingZone` runs at once (the panel's live LEGAL/ILLEGAL, which Open checks). A vehicle nobody drives gets the parking state and the parking neighbourhood the game would store on leaving it there (the game's wheel test; the neighbourhood of the parking lane under its wheels), so the game's hourly parking charge is priced by the new district.

`bay:<site>` for a vehicle takes the bay's middle (its first resolved point) when nothing stands there, else the free place on the paint nearest the middle (every half metre along each painted stretch where the whole vehicle fits), facing the way that puts the hatch to the pavement (the mod's hatch check), else along the paint. With every place taken it falls back to the middle and its refusal (or `clear`). For the player, `bay:` is the bay's middle. `commissary:<site>` is for the player only and puts them 1.5 m along the walk from the entrance nearest the bay (the first entrance while the bay isn't resolved) towards the street, facing the entrance. The walk is the NavMesh path from the entrance to the nearest driving lane (else to the bay; else straight away from the building's middle). `vehicle:<id>` is for the player only: 1.5 m out from the vehicle's side at the hatch (a truck's right, a cart's queue side), facing it.

**`commissary bay_candidates`.** For a commissary whose automatic bay search found nothing (the log's `Commissary <site>: no bay this load …` line), this lists where a truck could stand instead. Give exactly one of `site` (a commissary's id) or `address` (any building, written as the game writes it, `ba:street_<name>#<number>`). With `address` the origins are that building's entrances, searched as a commissary's would be, so a garage can be scouted before it goes into `data/commissaries.json`; the reply's `site` and `status` are then null. A spot is legal by the same probe the automatic search uses (`BaySnap`: the game's wheel test for the truck's wheels with their clearance, lined up with the parking lane and centred across it), nearest first: up to 60 candidates per origin at least 4 m apart, plus the automatic pick, which is always listed and may break the spacing, the limit or the radius. `status` is the stored bay's (`resolved`, `failed`, `pending`). Per origin: `kind` is `entrance` or `data`; `door` the entrance the walk starts from; `walk_start` is `door` when the door's NavMesh point has a short walk to the street, `cut off: <why>` when it hasn't (then the automatic search takes nothing from this entrance, but walks to each spot are still measured from the door), `unknown …` when the door isn't on the NavMesh, or `none …` for a point set in data. `parking_colliders` is how many parking lanes were read and `truncated` true if there were more than 512. From a point set in data with a `heading` (a nose-in bay in a lot), only places facing that way are listed and the automatic pick is the point itself when the truck stands legally there. `same_side` on an origin is set only for a point set in data: whether the point itself is on its nearest door's side of the street (null for an entrance). Per spot: `heading` is the lane's direction in degrees (as the log's "the lane along" figure), `distance` metres from the origin, `same_side` whether the straight walk from the door to the spot crosses no driving lane (Core `BaySide`, the rule since 13 October 2026: a bay is on its door's side of the street; null with no door), `walk` `short`, `too_long`, `no_route` or `unknown` (Core `WalkRule`: a complete NavMesh path at most 1.6 times the straight line plus 15 m is short), `walk_m` the path's length and `straight_m` the straight line, both null when not measured. `automatic` marks the spot the automatic search takes: the bridge runs that search itself (`BaySnap.Nearest` within 30 m with the same side and walk rules) over parking read at least 30 m out whatever `radius` is, and lists its pick exactly, in place of any spot within 5 cm of it, so the flag always marks the place a search would store now. A listed spot nearer than the pick and not otherwise rejected reads `not taken by the automatic search (…)`: the search passes over cells within 3 m of one it rejected for its side or walk. `rejected` says why the automatic search passes a spot over: `beyond the automatic search's 30 m`, `no entrance to check the street's side from, …`, `no driving lanes found round the door, …` (the side is unknown and the search waits; `same_side` is then null), `the door has no short walk to the street, …`, `the point set in data is across the road from the door, …`, `across the road from the door`, `too long a walk from the door`, `no walking route from the door`, or `farther than the automatic pick`; null for the automatic spot. To use a spot, put its `x`, `z` into `data/commissaries.json` as the commissary's `bay`; a measured bay wins over the search when it is on its door's side of the street (`same_side` true), and is logged as an error and left unused when it isn't. The bridge logs one line per call: `Commissary <site>: bay candidates within <radius> m (test bridge): from entrance x …, z …: N legal, S on the door's side, M the automatic pick; T ms.`, or `Building <address>: …` for an address. The `commissary` guard holds: an FT city.

**`shoot`.** The camera copies the game camera's settings and HDRP camera data, renders 8 frames into its own texture, then the PNG is written and the camera removed. The game changes buildings for its own camera, and the bridge undoes that for each frame of its camera and puts it back in the same frame, before the game's camera renders: the player's view is unchanged. Live sessions 3 to 6 saw facades as a pale see-through copy with a flat white-edged cut over everything in front (the player, the truck). The cause is the game's view-blocking fade (`ViewBlockingObjectManager` on the game's main camera; research note of 13 October 2026, `build/review-modround/ghost-research.md`). Every building, tree or bridge between the game's top-down camera and the player goes into camera-block mode: its renderers get `_Reveal` towards 0 (the ghost), hidden renderers go shadows-only, signs switch off and the building's bottom plane shows (the cut line). That is renderer state, so any camera sees it, and it came and went with where the player stood relative to the game's camera. For the bridge's frame (`TestBridgeUncover`):

- for each entity in the game's active list, at renderer level only: `_Reveal` is set to 1 in a copy of each faded renderer's property block; a blocked entity's hidden renderers (`renderersToHide`, its signs) are shown again (shadows-only back to casting, a disabled one enabled), and its bottom plane's renderers are disabled. Each renderer's exact property block, enabled flag and shadow mode is saved before anything changes and written back, each on its own. The building's logical block state, its layers and object activation are never touched (review round 10: the game's own toggles flip the flag first and `SetActive` objects, which can't be undone exactly), so the entity's `objectsToDisable` stay hidden in the shot;
- the hovered or highlighted building (live session 9: the game's idle cursor over 22 1st Street opened its card and drew it pale with a white edge, and the bridge's shot copied it): the building under the mouse (`CurrentBuildingHighlighted`, `MouseController.currentTargetEntity`), the one whose card is open (`BuildingResume.TargetController`) and any with a map-filter highlight colour. Their root, parts, LOD, ground plane and billboards go from `BuildingsOutlined` to the Buildings layer, and `_SelectionColor` is cleared in a copy of the property blocks of their `renderersToHide` and LOD; all saved first and written back exactly. The reply's `hovered` lists them (`<name> (under the mouse, its building card open, N objects outlined, selection colour)`), `asis_hovered` with `compare`;
- every object on the hover/map-filter outline layers (`BuildingsOutlined` for buildings within 250 m, `InteractiveItemsOutlined` for items) is moved to its plain layer and back to the exact layer it had;
- the game's BuildingHider globals (`GlobalPlayerPos`, `_PO_Height`, `_PO_Height_Offset`) are moved out of reach and back, as since 407e9a4; they weren't the ghost's cause, but the override costs nothing and is undone in the frame.

Each step is undone on its own in a `finally`, in reverse order, so one failure leaves nothing else changed. The reply's `uncovered` lists the entities lifted (`<name> (<type>, reveal 0.00, blocking the game's camera)`) and `outlined` the buildings and items whose outline was lifted; the shot's log line adds `; uncovered …; outline lifted from …`. `"compare": true` renders four more frames as the game has them, nothing undone, and writes `<name>-asis.png` (`asis_path`, with `asis_uncovered` and `asis_outlined` saying what would have been lifted then): the ghost in the as-is picture and not in the shot shows the cause. `state.view_blocked` lists what the game fades now and `state.game_camera` where its camera stands (`x`, `y`, `z`, `yaw`, `pitch`), so a check can stand the player where a building comes between them. A failed frame releases the shot's camera and texture (the pump now runs a failed call's cleanup too). `frames` (a whole number from 8 to 240, default 8) sets how many frames the camera renders before the picture is read; with the game in the background at a low frame rate, 240 frames can outlast the call's `timeout_s`, and the shot then comes back through its op id. `"game_view": true` also saves the game's own frame for that moment, with its camera and UI (`ScreenCapture`, at the end of the frame), as `<name>-game.png` (`game_path`, or `game_error` when the capture failed): ground truth for what the player sees, for example whether a truck that is black in a rain shot is black in the game too. `fov` defaults to 60. Vehicle poses use the truck's hatch (on its right, at the player's place behind it) or the cart's queue side; `bay-pavement` stands 6 m from the bay on its pavement side; `bay-road` stands on the driving lane nearest the bay, 12 m back along it, 1.5 m up, looking at the bay's middle (without traffic lanes, 12 m along and 5 m out from the bay); `door` stands 6 m along the walk from the entrance to the street (as `commissary:`), at eye height, looking at the entrance.

A named pose never starts inside geometry (live session 4: `vehicle-side` inside the facade where the pavement is under 6 m wide, `door` nearly black where the walk is cut off). Each pose has a list of ways round its subject, its own first; for each, a 0.25 m sphere is swept from the subject out towards the camera, and the first solid thing on the line (buildings, walls, roofs, large props; not the subject, people, vehicles, triggers, or things under 0.8 m across such as poles and signs) pulls the camera in to 0.4 m in front of it (Core `ShotClearance`). A way whose room falls below the pose's nearest distance, or whose camera place is inside anything (poles and vehicles included), is skipped. Ways, in order: `vehicle-side` the hatch side 6 m out, from above it (4 m out, 4.5 m up), the other side, from high above (9 m up), nearest 3 m; `hatch-pavement` nearest 1.2 m; `hatch-close` and `cart-counter` 0.8 m; `vehicle-overhead` from above behind, then straight above, 5 m; `queue` along the pavement, then from 4.5 m up, 4 m; `bay-pavement` the pavement, above it, the road side, 2.5 m; `bay-road` the lane behind, the lane ahead, above the lane, 4 m. `door` tries the walk first; if that isn't clear for its full 6 m it weighs every way out (towards the nearest lane and straight out, each turned 0, ±30 and ±60 degrees, at eye height and 3.5 m up) and takes the one with the most room, at least 2 m. The reply's `pose_note` is null when the pose's own way stood clear, else says what changed (`from the hatch side was blocked; taken from the other side`, `…, pulled in to 3.6 m in front of <object> (layer …)`); the shot's log line carries the same note in brackets. With no way clear the pose's own is used and the note says so. A free camera stands where it is put, and `pose_note` warns when that is inside something solid. `camera` gives where the camera stood and its angles. `fov` is 5 to 120 degrees.

For a truck the player drives, `legal` is the vehicle panel's live reading (`vehicleInfo.currentParkingState`, the one Open checks) and `legal_reason` reads `panel's live reading: Legal|Illegal|NotAvailable`; for any other truck it is the game's own wheel parking test (`Legality.VehicleLegallyParked`), `legal_reason` starting `wheel parking test:`; for a cart it is the mod's pavement rule (`Legality.Check`), `legal_reason` starting `pavement rule:`.
- `hatch_side` is `right` for a truck (where its hatch is); for a cart it is the side its queue formed on, null while no line is laid out. `hatch_to_pavement` is the mod's hatch check for a truck, null for a cart.
- `serving` is `player` when the sales tick counts the player at the window, `crew` when a crew member serves, else `nobody` (always `nobody` when closed).
- `pieces[].item` is the equipment id from the demand tables. `stock[]` lists the cargo that isn't equipment: `item` the game's name, `key` the item key.
- `queue` is null while closed. `length` is Core's customers at the window and in line; `places` are the spots the visible line uses (empty while it isn't shown), `occupied` for the first `length` of them.
- `commissary` is null unless the vehicle has a space or stands in a bay; `site` is its space, `in_bay` whether it stands in any bay (legally parked for a truck, within the radius and on the door's side of the street, as the mod's own test: `Commissary.InBay`), `bay_site` which one.
- `parking` is what the game's hourly parking charge reads for the vehicle when nobody drives it (`ParkingSimulator.RunHourly`): its stored `state` (`Legal`, `Illegal`, `NotAvailable`), the `neighbourhood` it was left in, that neighbourhood's `hourly_price` (null when the neighbourhood is unknown) and the `unpaid` amount the game bills at midnight.
- `route` is null without a week plan (no stops and no shifts). `route.stops` counts today's stops (the game's weekday) and `route.next` is a line of text, "stop N, HH:MM to HH:MM at x …, z …", for today's first stop still to close, N its number on today's route. `route.week` is the week plan, Monday first: each weekday's `closed` mark (the day tile's tick box), its `stops` with their hours and place, its `route_day` (from the morning restock in the commissary bay to back in the bay, as minutes from that weekday's midnight, past 1440 for a late route; null on a day without a route) and its `gaps`, the parts of the route day with nobody of the crew on shift, in the same minutes (Core `WeekPlan.Gaps`). `route.shifts` has one entry per crew member: `employee` (name), `id`, `week_hours` (the hours of all their shifts, as the game's job demands read them), `wants_min`/`wants_max` (their `HoursWorkingPerWeek` demand, null without one) and `shifts` (weekday, start and end hour, end exclusive, at most 24, and `station`: the row on the Schedule tab, `serving1` or `serving2`). `route.problem` is Core's `HireRunner.RouteProblem` in snake case (`overlap`, `bad_times`, `unreachable`, `uncovered`, …), null when the mod data isn't loaded. The mock's routes run one stop every day with no shifts and no commissary.
- `commissary.orders[]` adds `item` and `units`; `total` is goods plus fee (0 while the order waits: the delivery's flat fee is set when it arrives). `commissary.stock[]` adds `key`. `unpaid` sums the rent and fines the game refused.
- `todos` lists the to-dos the mod has in the phone for that vehicle (`VehicleTodos`), as the last game minute's reconcile left them, each with `text`, the line the phone shows (a `route_problem`'s names its cause: the stops' times, the stop it can't reach, or the days and hours with nobody on shift, Core `RouteCause`): `kind` is `low_stock`, `empty_stock`, `missing_crew`, `route_problem`, `no_permit`, `no_commissary_space` or `health_grade_c`, `item` the food for the two stock kinds and null otherwise. `licence.todos` holds the fleet's one, `licence_running_out` or `licence_expired`. The reconcile runs once a game minute, so a change made while the game is paused shows after the clock moves. The mock makes none. Built, not yet run in game.
- `commissary.bays` has every commissary: `resolved` with the bay's first point and the building's entrance nearest it, `failed` when the search found no legal parking (a stored failure is searched again once on every load, and stays `failed` until a search finds a bay), `pending` until the city's parking lanes let it search. `shoot`'s `door` pose and `teleport`'s `commissary:` use that entrance.
- `transactions_today` is the game's transactions of today and yesterday, oldest first; `label` is the transaction type resolved with its data, as close to the bank app's text as the bridge can read it. `balance` is the game's balance after it, floored to whole dollars; it tells two equal transactions apart.
- `player.handtruck` is null unless the player pushes an ordinary hand truck or flatbed; otherwise it has the same entry as `handtruck list`, including the cargo shown in its panel. Food carts remain in `vehicles`.
- `employees` are the hires the crew dropdown offers (hired, without a building or vehicle), best customer service first.
- `load` is null before the first `load` call.
- `ledger_today.street_food` is today's street food revenue in the mod's ledger; `sales_waiting` is all player and crew takings not yet paid in, across saved days. `crew_waiting` remains an alias for compatibility. Both kinds accrue without per-sale balance changes and pay together at midnight, one payment per vehicle/day (`foodtrucks:transaction_crew_sales`, now labelled "Street food sales: …"). `day_summary` records sales on their sold day regardless of payout timing.

## Playthrough runner

`tools/playthrough` runs the AI playthrough of `docs/ai-playtest-plan.md` on top of the bridge. It runs only in a loaded save whose name starts with `FT playtest`, and it stops at the first hard failure, which it writes to `build/playtest/<run>/run.json` as `stopped`. It has two modes.

**Blind play (the tester).** Peter wants the AI tester to play blind: controls only, no balance data, no Core code, no plan telling it where to go. It learns by playing. Its only interface is `tools/play`, a whitelist over the bridge with plain output; `tools/play --help` is the player's manual, with a short "How the city works" section of hints (needs, a home, taxis, the licence's course and call, hiring) and no numbers. Since 17 October 2026 (after blind run 2) it plays the game's own mechanics, with no shortcuts: `go ADDRESS` is the game's taxi (`taxi`, after a taxi in the street was clicked with `use`: fare and ride time), `time until` passes `keep_needs: false` so hunger and energy run down, `use` clicks things in the world (shops' shelves and tills, a school's doors, a bed, building entrances, which also offer a building for rent), `eat` eats from a bag in hands, `place` sets down a bought bed in a rented home, `phone APP` and `call CONTACT` reach the phone (the City of New York's licence and permits; the recruitment agency; candidates in the employees app), `ui set` moves sliders (hours of sleep or study), and `walk --to exit` leaves a building. Allowed besides: `look` (state as the player sees it, with how the player feels and what they hold), `notices`, `places`, `map`, `walk`, `screen` (the game's own frame), `ui list|click|set|escape`, `time pause|speed|until` (speed at most 20), `buy truck|cart`, `vehicle ID open|close|enter|exit|back_to_hatch|work_window|stop_work|fast_forward|skip_work|restock|rent_bay|take|return`, `order`, `crew assign|schedule|auto`, `price`, `route add|paste`, and `save` and `load` of `FT playtest…` names. The debug `licence` and `hire` are gone from it. One shortcut is left on purpose: `buy truck|cart` is the debug spawn beside the player, paid at the dealer's price as the dealer books it (`vehicle buy`), because the tester can't drive a truck home from a dealer yet (Phase B's rides). Nothing else is reachable: no money, teleports, spawns, fixtures or debug actions. It needs only its own folder: copy `tools/play` with `tools/ftlib/bridge.py`, `paths.py` and `__init__.py` (and `shots.py` for `screen --fetch`). With `FT_PLAY_STOP` set to the referee's STOP file, every acting command refuses once the file exists and prints the reason.

**Hands and hand trucks (blind run 3).** `tools/play drop [X Z]` puts down a closed box or bag without unpacking it; `place X Z` still unpacks furniture. `pickup ID` uses the latest `use` list. `handtruck` lists nearby ids and cargo; `handtruck ID grab`, `handtruck release`, `handtruck ID load` and `handtruck ID take ITEM` use the paths above. Taking while pushing lets go as the game's cargo panel does. `look` names the pushed hand truck and lists its cargo (names, counts and paid flags only). These commands print no cargo purchase prices or hidden balance/tuning values. Each acting command honors `FT_PLAY_STOP`, and walks run at speed 1 with the previous clock setting restored afterward. To free hands away from an editable building, load a hand truck and release it before using the cashier; the game does not offer general street dropping. All game-side behavior here is **unverified in game**; no SDK build or PC connection was performed for this change.

**The player's life, in the mock.** `tools/mock-bridge` models enough of it for `tools/play`'s tests: a taxi always 8 m away, building entrances (a residential building without a business is for rent at $60 a day and $300 deposit), fast food restaurants and coffee shops with a till that sells into a paper bag, supermarkets and furniture stores with shelves into a box paid at the till, the school's Market Demands door with the Food Safety course (6 hours at the rules' price, a slider of hours), the school's Basic HR door (a made-up 4 hours), the recruitment agency's receptionist (who refuses without Basic HR, and without a business or a food vehicle; with a food vehicle the mod's "Street food fleet" campaign form: business and skill options, part and full time toggles, deadline and candidates sliders, the game's price), candidates arriving unassigned at their find hours, the City's licence and permits by phone, a bed set down with `place` and slept in with the slider and Start (0.35 energy a minute). It has no recruitment campaign: tests put a candidate in the employees app by hand. Its shop goods and prices are made up. It also models packed-container drop/pickup, hand trucks in rented flats, release/regrab, whole cargo-box transfers, partial/full-capacity refusals, and the full-hands cashier refusal while pushing. It cannot establish Unity placement geometry, navigation, UI bindings or persistence in a real save.

**The referee.** `tools/playthrough watch --run NAME [--stop-file F]` runs beside the tester and changes nothing. After each in-game 05:00 it takes a snapshot, appends the ledger and runs the checks. On a hard failure it pauses the game and writes the reason to the STOP file (default `build/playtest/<run>/STOP`). It learns the tester's orders and vehicle purchases from the state and the game's transactions. It leaves alone the vehicle the player is in or at, and vehicles without a crewed route.

**Scripted mode, for our own runs.** `setup` and `run` drive the game from a plan file.

```sh
tools/playthrough setup tests/game/playthrough/phase-a.json --run phase-a-1
tools/playthrough run --run phase-a-1 --days 6
tools/playthrough check --run phase-a-1 --log build/logs/game/<session>/Player.log
tools/playthrough report --run phase-a-1
```

`setup` (with the plan's optional `starting_money`, which `phase-a.json` leaves out: the fresh character plays with its own money) teleports the player to the commissary's door, buys each vehicle with `vehicle buy`, puts it in the bay and rents a space there, grants the licence and permits with the `licence` debug action (free), hires each crew with the `hire` debug action, orders the equipment and food (at most 10 boxes an order), and adds each stop by address on every day. It saves `FT playtest d<day>`, runs the clock to 08:05 on the delivery day, gets into each vehicle in the bay, takes each piece of equipment from the commissary's stock, fills up and parks, and only then runs the auto schedule, so no wages are paid while there is nothing to sell.

`run --days N` runs the clock at speed 20 to each next 05:00, takes a snapshot (`state` and `day_summary` for today and yesterday, plus new events), checks it against the one before, saves `FT playtest d<day>`, and every 7th day (`--reload-every`) loads that save again and checks that money, stock, crews and pieces came back the same. A plan's `changes` (a pasted day, a moved shift) are made on their day. With the plan's `growth` on, the run buys the next vehicles (a truck in `phase-a.json`) with their crew, stock and stops at the first 05:00 when money less `reserve` covers their price, and fits them after the delivery the next morning. `phase-a.json` starts like a player: one cart, its space, crew, stock and route; growth is off there.

The checks, between each pair of snapshots. Hard failures stop the run:

- money: the change in money is the sum of all the game's transactions booked in between (`transactions_today`, as a multiset), within a cent plus a fifth of a cent per transaction for the game's float rounding;
- books, for each finished day, only the mod's own lines: the sale, crew sales and catering transactions against the ledger's sales, the commissary rent, overnight fines, and the commissary order payments against the delivered goods and the delivery fee. The game's other transactions (the apartment's rent, taxes) are left out. Wages and vehicle purchases above the crews' and the runner's (another hire or vehicle) are a note; below them, a failure;
- stock, per food: each commissary and its vehicles hold what they held, plus what was delivered, less what was sold; a vehicle never holds less than it started with less what it sold (crews only load);
- moves, at 05:00: every vehicle stands in its own commissary's bay, or within 30 m of a stop of yesterday's route that runs past midnight, and is closed;
- log: no `ERROR: ` line among the events, and no Unity error naming a FoodTrucks type. The game's own Unity errors are notes.

Notes don't stop the run; they go to `run.json` (`notes`) and the report: a refused commissary delivery, a route Core finds a problem with, other wages or vehicles, and (for the referee) days it couldn't reconcile because more than a day passed between two looks. `ledger.csv` has a `game_other` column for each day's other game transactions.

`ledger.csv` has one row per finished day and vehicle and one for the fleet's own lines, money in dollars. `check` runs every check on every window of the snapshots offline, each on its own, and lists every failure rather than stopping at the first. A window whose snapshots lack what a check needs (no commissary block, sold counts already gone, more than a day between looks) is "not checkable" for that check. It rebuilds `ledger.csv` from the snapshots, writes `check.json`, and runs the log rules on a `Player.log` with `--log`. An order the snapshots never showed waiting counts as delivered only in the window its 08:00 delivery falls in; blind-1's first check counted every later order of the run as delivered in its first window. `report` writes `report.md`: the result, what was played, daily profit per vehicle, the findings, and the week's revenue per vehicle against `tools/balance --reports playthrough` for the same foods, stops and hours (`--balance auto`, the default; `off`; or a JSON file). A gap beyond ±25% is reported, never failed.

The mock models enough for these checks to mean something: every charge is a transaction, the commissary's rent each midnight, wages for each shift hour at midnight, deliveries, the crew's morning load in the bay, one sale every ten minutes at each stop, and the drive back. Its numbers are made up, so its balance gaps say nothing. A vehicle bought at a commissary's door lands in its bay in the mock; in the game the spawn puts it beside the player, and whether a cart there counts as in the bay is unchecked. A blind tester has no control to drive or push a vehicle into a bay (Phase B's Self Driving rides). Nothing of the runner, `tools/play` or the referee has run against the game.

## Scenarios

A scenario is a JSON file in `tests/game/scenarios/`. `tools/scenario run <file>` runs its steps in order and stops at the first failed check unless the step says `"soft": true`. Reports go to `build/scenarios/<name>-<time>/` (`report.md`, `report.json`, `events.jsonl`, and the shots fetched from the PC).

```json
{
  "name": "commissary-pay-on-delivery",
  "checks": "CHECKS.md, Commissary look and payment (0.9.10), rows 1 to 3",
  "needs": { "scene": "city", "save_prefix": "FT" },
  "steps": [
    { "call": "debug", "args": { "action": "spawn truck" } },
    { "call": "money", "args": { "set": 20000 } },
    { "remember": "money", "from": "state", "path": "money" },
    { "wait_event": "Commissary order \\d+: 2 boxes", "timeout_s": 30 },
    { "expect": "state", "path": "money", "equals": "$money" },
    { "call": "time", "args": { "run_until": { "day": "+1", "time": "08:05" }, "speed": 20 } },
    { "wait_state": "clock.time", "equals": "08:05", "timeout_s": 300 },
    { "expect": "state", "path": "commissary.orders", "length": 0 },
    { "shoot": { "name": "bay-day", "pose": "bay-pavement", "target": "bay:hells-kitchen" } },
    { "note": "Rows 6 to 9 need eyes: see the contact sheet." }
  ]
}
```

Step kinds: `call` (with optional `expect_ok: false`), `remember` (a value into `$name`), `expect` (`equals`, `not_equals`, `less`, `greater`, `length`, `contains`, `matches` on a dotted path of `state` or of the last call's result), `wait_event` (a regex over new events), `wait_state` (poll `state` until a path meets the condition), `no_event` (a regex that must not appear between two steps), `shoot`, `sleep_s` (real seconds), `note`. Paths are dotted with list indexes (`vehicles.0.stock.1.amount`) and filters (`vehicles[kind=truck].legal`).

## Log checks

`tests/game/logchecks/<version>.txt` holds a build's expected log lines, one per line:

```
# id | rule | regex
patch.runDaily | must | Patch BusinessHelper\.RunDaily: Active\.
crew.paidIn | must | Street food sales paid in: .+, day \d+: \d+ items
no.notActive | never | Patch .+: Not active
```

Rules: `must` (at least once), `never`, `count=N`, `count>=N`, `order` (the regexes listed on one line separated by ` >> ` appear in that order). `tools/check-log <Player.log> [<version>]` also always reports every `Patch …: Active.` and `Not active` line, every mod error line and every exception that names a FoodTrucks type, and exits non-zero on any failed `must`, `never` or `count` rule. Without a version it takes the version from the log's `Version … loading.` line.

Dots build nested arguments. `--json` before `call` prints the raw reply; after `call` it supplies arguments. `call --raw` also prints the raw reply. `wait-event` watches new events. Event cursors are inclusive: request `since` and later, then use the reply's `next` unchanged. Every health, events and call reply, including operation status results, carries a `session` string that changes each bridge start. The client remembers the first reply's session and sends it as the top-level `expect_session` field on every subsequent `/call`. A mismatch returns `ok: false` with `the bridge restarted (session <new>); reconnect first.` and the new session; the command is not run. The client detects a changed session even if the new event counter has already passed the old cursor, then blocks further calls locally until reconnect. An active scenario fails immediately, including soft steps and `--keep-going`, and clears remembered values; events and remembered values from before the restart are void. Start a fresh scenario run. `ft events --follow` announces a restart on stderr and resumes from event 1 in the new session. A lower `next` than the cursor remains an additional restart check.

Row rules count only for selected `--rows`; `--rows all` checks every row. Rules without rows always count. Every `[Mod:Food Trucks] ERROR: ` line (also the older unspaced prefix) fails the always-on error check; older logs keep the word and stack heuristics. Unknown versions get only the always-on checks. Conditional diagnostics use `count>=0` to report observed counts without requiring a fallback or retry.

The mock mirrors the built command guards, errors, result shapes, null fields, asynchronous entry and inclusive events. It simulates the economy and writes valid PNG placeholders; it cannot model Unity navigation or rendering. Its normal clock is one game minute per real second; `--clock-rate 100` emulates a faster Options setting for tests without changing command speed semantics. Tests use a free loopback port and never connect to the game PC. In environments that forbid listening sockets, `FT_TEST_TRANSPORT=inprocess python3 -m unittest discover -s tools/tests` exercises the same HTTP handlers and JSON replies in memory, with MCP tested over stdio pipes. This does not verify socket transport.

`save` returns name, path and bytes only after serialization, compression and a fresh nonempty file succeed. Failed saves remain failed operations. On unload, queued and deferred work fails with `the bridge stopped`, operation and event history is cleared, and event numbers start at 1 on re-enable.

Every normal command reply carries an `op` id, also shown by readable `ft call` output and in MCP results/errors. `ft op N` and MCP `ft_op` query it without creating another operation. `timeout_s` is clamped to 1..600 seconds by both client and bridge. After a main-thread timeout the client polls that id for up to 30 seconds and returns the original result or failure. It never repeats the command. If it stays pending, query the id later. A transport failure before an id arrives has an unknown outcome; inspect the game log before repeating a mutation. The bridge keeps every pending operation and the last 500 completed operations. Invalid request bodies and op queries have no new op id.

`.mcp.json` registers the stdio server as `foodtrucks-game`. It uses the same environment variables and fetches screenshots into `build/shots/`. The MCP server is one Python process for the whole agent session: it loads the tools' code when it starts, so after `tools/` changes it keeps running the old code until the session (or its MCP server) restarts. `ft_reconnect` only pins the bridge's new session; it doesn't reload any code. Live session 5's server was older than the tools and had no `look_at`. The MCP client persists between tool calls. After a restart, `ft_health` keeps working and adds `restarted`, `reconnect_required`, the previous session and a message; it does not reconnect. Use `ft_reconnect` to pin the current session and discard old operation ids and event cursors. Resume with events `since: 1`, fresh operation ids and fresh scenario values. Known old ids and cursors are refused locally until issued again in the current session. A failed reconnect leaves calls blocked. The CLI starts fresh for each invocation, so it has no reconnect command.
