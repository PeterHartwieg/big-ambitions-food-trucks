# Event addresses, 0.10.8

City event locations are curated building address IDs in `data/pitches.json`, resolved to native entrance positions by `World`. The offer, reminder, booking confirmation, phone and arrival notices previously displayed separate labels without building numbers. Those labels use written street names instead of the native map spelling. No arbitrary event coordinates are generated.

Catering offers are selected from native building entrances, including park-adjacent buildings. `Catering.PlaceName` previously split the internal `street#number` ID and sent the street ID through Localizor. Street IDs are not locale keys: the game reads `StreetData.streetLocalization` through `Streets.AddressHelper`. This could expose raw IDs even though the underlying building exists. The player's exact screenshot/save was not supplied, so this is a confirmed code defect and likely explanation, not a reproduction of their particular save.

`EventLocations` resolves the exact building and calls its native address formatter, shared with the game map. Missing or unresolved street data is rejected before offering/booking. City-event notices and phone text share that resolver. Catering descriptions share it too, covering offers, confirmations, missed and paid notices. A missing location displays a readable unavailable label instead of an ID. Stored phone repair is restricted to catering offers/booking confirmations and city announcements, booking confirmations and reminders whose place contains `:`, `#`, `{` or `<`, or equals the unavailable label. Readable places and terminal notices are untouched. New payloads include stable booking and location IDs. Legacy repair compares day/start/kind plus every available guests/end/fee/food field, and requires the stored place to match the candidate's known old location rendering. A sole surviving offer is never enough evidence by itself. Multiple matching candidates are left untouched. Legacy same-day city reminders use their own native timestamp day when their payload lacks `day`; new reminders carry `day` explicitly.

City-event phone entries retain fully booked events and offer Set destination through the native address guider. Native `GuidersManager.SetGuiderTarget(Address, Destination)` persists `SaveGameManager.Current.customDestination` before setting the target, so the adapter uses that existing path. A single event's directions card offers Back; multiple events offer Next event. Both event families explain their existing map highlight: Street food > Premium spots and events, or Catering bookings. The native map search indexes only buildings with business names, so an address existing in the game does not guarantee a search dropdown result; the highlight and city-event GPS avoid relying on that search.

When native addresses are ready, invalid city events are cancelled before expiry. The Core helper `CityEvents.UnusedPlaceRefund` refunds `max(0, Booked - distinct vehicles in Holds) * FeeCents`, equally for future, running and ended events. Repeated holds by one vehicle count once. Invalid booked or started catering work is removed before departure/no-show judgement without changing reputation, failure counts, money or stock. Earned unpaid fees are retried above the address gate; started-gig settlement is also called above it, deferring departure judgement while buildings are still loading. This does not reverse past penalties already archived in old saves; those do not retain proof that the address caused the miss. Save schema remains 2; no new Core state fields or binary dependencies. Additional identity fields live in the native message payload dictionary.


City readiness gates only address-dependent work. Expiry, premium-hold pruning and load-only closed-vehicle hold release still run when street/building data is absent. `CityPitchRetry`, attached to the session runtime, retries the deferred city work as soon as addresses become ready; detach clears the pending state. Building controllers are cached by address key in `World` and cleared by `Reset`; catering offer generation validates the controller it already holds. Catering confirmations use the configured `{metres}` radius, and radii use invariant integer formatting. Cancellation texts identify the kind, weekday/day and start time.
